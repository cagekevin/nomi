# 05 · Nomi 的「三层架构」到底指哪三层 —— 给开发者的心智地图

> 配套：`02-开发上手-2026-08-10.md`（启动/命令/目录）、`docs/architecture/`（各子系统）、`AGENTS.md`（纪律总纲）。
> 这份文档解决一个真实困惑：**Nomi 文档里到处说「三层」，但说的不是同一件事。** 不把这几种「三层」分清，你会在错误的层动手改代码。

---

## 0. 先给结论（一分钟版）

Nomi 语境里至少有 **三套互不相干的「三层」**。开发者最容易踩的坑，是把「进程三层」误当成整套架构，结果在渲染层去改本该在主进程跑的能力。

| 叫什么 | 它回答的问题 | 你改代码时该用哪套 |
|---|---|---|
| **A. 进程三层（物理边界）** | 代码跑在哪、能碰 Node 吗 | 决定「这个能力写在 main 还是 src」 |
| **B. 生产系统三层（逻辑架构）** | 一个 AI 视频项目怎么从文本变成成片、且可复现 | 决定「这个功能落在 Memory / Graph / Agent 哪一层」——**这是 PRD 的护城河，也是理解整个代码库的钥匙** |
| **C. 设计 token 三层（视觉真相源）** | 一个颜色/字号从哪来、能不能硬编码 | 决定「这个视觉值写哪个文件」 |

> **给开发者的第一性判断（D3）**：A 是「地板」（运行边界，必须遵守），B 是「骨架」（产品逻辑，决定你东西放哪），C 是「皮肤」（视觉纪律，门岗会卡）。A 不等于 B——进程分层只是把 B 的三层分别装进了不同的进程盒子。

---

## 1. A 套：进程三层（物理边界）—— 你已经知道的，但常被误读

这套在 `02-开发上手` §3 已写，这里只补**容易误读的点**。

```
主进程 electron/  ──IPC──►  桥 preload.ts → window.nomiDesktop  ──►  渲染进程 src/
(Node 运行时)                  (contextBridge 唯一出口)              (Chrome/React 运行时)
```

- **主进程**（`electron/`）：能碰文件系统、能 spawn ffmpeg、能调模型供应商、能写 user-data。
- **桥**（`electron/preload.ts` + `src/desktop/bridge.ts`）：渲染层**永远不直接碰 Node**；所有主进程能力经 `nomiDesktop.*` 暴露。加新能力要改三处：`main.ts` 注册 handler → `preload.ts` 暴露 → `bridge.ts` 加 TS 封装。
- **渲染进程**（`src/`）：只画 UI、只持临时状态（Zustand），重活经 IPC 委托给主进程。

**误读警示**：进程三层是「运输容器」，不是「业务分层」。一个「Agent 自动把剧本变成画布节点」的功能，物理上会**跨三个进程**（渲染层发指令 → 桥 → 主进程 Agent Runtime 跑 → 写回 Memory → 经桥通知渲染层重绘），但逻辑上它纯属 B 套的「Agent Runtime Layer」。别因为功能从渲染层触发，就把它写进 `src/`。

## 2. B 套：生产系统三层（逻辑架构）—— 真正该刻进脑子里的那套

出处：`docs/archive/2026-05-shipped/nomi-differentiation-prd-2026-05-23.md` §4.3「三层生产系统 = Nomi 核心护城河」。这是产品定位文档明确定义的架构，且**代码里确有对应落地**（不是空想）。

```
┌──────────────────────────────────────────────────────────────────┐
│ ③ Agent Runtime Layer  —— 「下一步怎么自动执行且可审计」            │
│   读取项目状态 → 提计划 → 调工具 → 写回变更 → 记日志 → 等确认       │
│   代码落点：electron/runtime.ts · electron/ai/* · capabilityCore/*  │
│            · electron/productionRun/* · src/workbench/production/*  │
└───────────────┬──────────────────────────────────┬───────────────┘
                │ 读/写                              │ 读/写
                ▼                                   ▼
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│ ② Production Graph Layer          │   │ ① Project Memory Layer           │
│   画布 DAG + 时间轴 = 生产图       │   │   剧本/角色/场景/镜头/资产/       │
│   不只是 UI，是「素材怎么变成成片」│   │   调用证据 的持久真相              │
│   代码落点：                       │   │   代码落点：                      │
│   src/workbench/generationCanvas/*│   │   electron/projects/repository.ts │
│   src/workbench/timeline/*        │   │   electron/conversations/*        │
│   src/workbench/generationCanvas/ │   │   electron/memory/*               │
│     store/generationCanvasStore.ts│   │   electron/assets/*               │
│   capabilityCore/canvasGraph.ts   │   │   （Zustand store 只是它的内存投影）│
└──────────────────────────────────┘   └──────────────────────────────────┘
```

### 2.1 为什么这三层是护城河（不是堆功能）

PRD 原话的底层逻辑（D3 第一性）：

> 用户不是在 Nomi 里临时生成几张图，而是在 Nomi 里**经营一个可长期演化、可复现、可迁移的 AI 视频项目**。

- **Memory Layer** 回答「这个项目发生过什么」——换供应商、换模型，历史不丢。
- **Graph Layer** 回答「素材怎么一步步变成成片」——生产图是 DAG，不是一串按钮点击。
- **Agent Runtime Layer** 回答「下一步怎么自动执行且可审计」——Agent 读 Memory、改 Graph、写回 Memory，全程留痕。

三层正交：Agent 可以换（规则引擎/LLM/外部 MCP host），Graph 可以换布局，Memory 可以换存储——**只要接口在，彼此不连坐**。这正是 P4「通用第一」+ P1「无并行版」在架构层的体现。

### 2.2 代码落点速查（开发者最关心的「在哪改」）

| 你要动的 | 落在 B 套哪层 | 主要文件 |
|---|---|---|
| 剧本/角色/场景/镜头档案 | ① Memory | `electron/projects/repository.ts`、`electron/conversations/*`、`electron/memory/*`、`electron/assets/*` |
| 画布节点/连线/DAG 语义 | ② Graph | `src/workbench/generationCanvas/store/generationCanvasStore.ts`、`capabilityCore/canvasGraph.ts`、`src/workbench/timeline/*` |
| 时间轴剪辑/转场 | ② Graph | `src/workbench/timeline/*` |
| Agent 拆镜头/出计划 | ③ Agent Runtime | `electron/runtime.ts`、`electron/ai/*`、`src/workbench/generationCanvas/runner/generationRunController.ts` |
| 把 Nomi 当 MCP 给外部 Agent 调 | ③ Agent Runtime（出口）| `electron/capabilityCore/*`、`electron/productionRun/*`、`src/workbench/production/*` |
| 模型接入/供应商适配 | ③ 调度的执行端 | `electron/catalog/*`、`electron/providerAdapter/*`、`electron/runtime.ts` |

> 注意：**Graph 的「真相」在主进程**（`capabilityCore/canvasGraph.ts` + repository），渲染层的 Zustand（`generationCanvasStore.ts`）只是它的内存投影与交互缓冲。改 Graph 语义先去主进程找真相，别只在 `src/` 里改 store——那是症状层（P2）。

## 3. C 套：设计 token 三层（视觉真相源）—— 门岗会卡的那套

出处：`docs/design/nomi-design-system.md` §「值的真相源（三层，按优先级）」。这是**视觉值**的分层，和前两套完全独立，但开发者写 UI 时天天撞上。

| 层 | 文件 | 前缀 | 你能不能直接用 |
|---|---|---|---|
| ① 规范底层（**唯一该新增的地方**）| `src/theme/nomi-tokens.css` | `--nomi-*` | ✅ 新颜色/圆角/阴影只加这里 |
| ② 工作区语义映射 | `src/workbench/workbench.css` | `--workbench-*` | ✅ 工作区内语义色（success/danger/video/hover）用这层，alias 到 ① |
| ③ 遗留并行命名 ⚠️ | `src/styles/globals.css` | `--tc-*` / `--handle-color-*` | ❌ 别再用、别再加，早期暗色残留，多数已死 |

**铁律**：新增 token 只进 ①。`check:tokens` 门岗会直接红掉任何硬编码 hex / 随意 px。`--tc-*` 当历史包袱，看到别扩散（这是 P1「加新必删旧」在 CSS 的实例 R10）。

## 4. 三套三层怎么对应（一图防混）

```
            物理进程 A                      逻辑架构 B                    视觉 C
   ┌─────────────────────────┐   ┌─────────────────────────────┐   ┌──────────────────┐
   │ 主进程 electron/         │   │ ③ Agent Runtime             │   │ ① --nomi-*       │
   │   · runtime / ai         │──►│   · runtime.ts             │   │    (规范底层)     │
   │   · capabilityCore       │   │   · capabilityCore/*        │   │ ② --workbench-*  │
   │   · projects(repository) │──►│ ① Memory · ② Graph 真相     │   │    (语义映射)     │
   │   · catalog / export     │   │                            │   │ ③ --tc-* ⚠️      │
   ├─────────────────────────┤   └─────────────────────────────┘   │    (遗留,禁)     │
   │ 桥 preload/bridge        │                                      └──────────────────┘
   ├─────────────────────────┤
   │ 渲染进程 src/            │──►│ ② Graph 的 UI 投影 + ③ Agent 的  │
   │   · workbench/* (UI)     │   │   人机交互面（发指令/看结果）    │
   │   · design/* (token ①)   │   │ ① Memory 的 UI 投影            │
   └─────────────────────────┘   └─────────────────────────────┘
```

**读法**：纵轴是 A（物理），横轴是 B（逻辑），C 是横跨两者的视觉纪律。一个功能同时占三个坐标：比如「在画布上点节点看生成结果」——物理在渲染进程（A）、逻辑属于 Graph Layer 的 UI 投影（B②）、视觉必须用 `--nomi-*`/`--workbench-*`（C①/②）。

## 5. 对开发者的 6 条启示（落到日常改码）

1. **先判物理层（A）再判逻辑层（B）。** 要碰文件系统/ffmpeg/模型供应商 → 必在主进程；纯展示 → 渲染进程。但「在哪跑」和「属于哪层逻辑」是两问，分开答。
2. **B 套才是架构地图。** 拿起一个需求先问：它改 Memory（①）、Graph（②）还是 Agent（③）？落错层 = 平行实现/重复真相源，直接撞 P1/P2。
3. **Graph 真相在主进程，store 是投影。** 改 DAG 语义去 `capabilityCore/canvasGraph.ts` + `electron/projects/repository.ts`，别只在 `src/` 的 Zustand 里改——那修的是症状（P2）。
4. **Agent 层是「可替换的执行者」。** 不管内部是 LLM、规则、还是外部 MCP host，对外契约（读 Memory→改 Graph→写回→留痕）不变。加新 Agent 能力别新开一套 UI，复用现有 production run 面（P4 通用第一）。
5. **视觉值只认 C①/②。** 任何 hex、随意 px、`--tc-*` 都进不了 `check:tokens`。新视觉先去 `src/theme/nomi-tokens.css` 加 token。
6. **三层正交 = 改一层不连坐其他层。** 这是设计红利：换供应商只动 `catalog/providerAdapter`，换 Agent 只动 `runtime/ai`，用户数据毫发无损。守住接口，就守住了这个红利。

## 6. 常见误解（踩过才写的）

| 误解 | 真相 |
|---|---|
| 「Nomi 架构就是主进程/渲染/IPC 三层」 | 那是物理边界 A。真正产品架构是 B 套的 Memory/Graph/Agent，且横跨三个进程。 |
| 「画布是 UI，state 在 React store 里就是真相」 | 画布 DAG 真相在主进程（`canvasGraph.ts` + repository），Zustand 只是投影。 |
| 「Agent 是独立功能模块」 | Agent 是 B③ 一层，横切 Memory 与 Graph；它不是「一个功能」，是「一种执行者」。 |
| 「设计 token 三层和架构三层是一回事」 | 完全无关。C 套只管视觉值的来源优先级。 |
| 「三层护城河是 PRD 口号，代码没落地」 | 落地明确：repository(Memory) / generationCanvasStore+canvasGraph(Graph) / runtime+capabilityCore(Agent)。改代码时它们就是你的坐标系。 |

---

## 7. 上手建议

1. 读 `02-开发上手` 建立 A 套（进程）直觉。
2. 回到本篇，把任何要改的功能**先归到 B 套的一层**（Memory/Graph/Agent），再定物理落点（A）。
3. 写 UI 时切到 C 套纪律（`check:tokens`）。
4. 多文件改动先写 `docs/plan`（R4）：范围里明确「动 B 的哪层、跨不跨 A、视觉走 C 哪层」。
5. 改完五门全过（R11）再 commit。

> 一句话收尾：**A 是地板，B 是骨架，C 是皮肤。分不清 B 的开发者会在渲染层重写主进程该管的真相；分不清 A 的开发者会把 Node 能力塞进浏览器。三层都分清，Nomi 才是可演化的，不是一堆临时拼凑的功能。**
