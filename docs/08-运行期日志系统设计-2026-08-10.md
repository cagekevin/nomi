# 08 · Nomi 运行期日志系统（Runtime Logger）设计

> 配套：`05-架构三层探索`（进程边界）、`electron/crashLog.ts`（崩溃落盘）、`electron/events/eventLogRepository.ts`（per-project 事件日志）、`electron/shared/ipcChannels.ts`（域单一真相源）。
> 状态：**设计 + 落地计划（待实现）**。本文件是 R4 意义上的「执行前文档」。
> 版本：v3（2026-08-10 ROI 重算）——v2 审计后按 ROI 砍掉过度工程：全链路 traceId 续链→降级为 IPC 边界 callId；删 msg 前缀；删渲染环形缓冲；新增导出包 meta.json + bridge 自动记耗时。详见 §7 变更记录。

---

## 0. 先给结论（一分钟版）

Nomi 今天有**两套已有日志设施**，但它们**都不是「运行时诊断日志」**：

| 设施 | 文件 | 它记什么 | 它不是什么 |
|---|---|---|---|
| 崩溃日志 | `electron/crashLog.ts` | 主进程未捕获异常 / 渲染崩溃 | 不是日常诊断日志（只落崩溃） |
| per-project 事件日志 | `electron/events/eventLogRepository.ts` | Agent 评测轨迹（append-only JSONL） | 不是通用 logger（只 harness 写，且 redact 后才落盘） |

而**产品代码至少 ~95 处 `console.log/error/warn/info`**（主进程 `electron/` 约 55 + 渲染 `src/` 约 40；`evals/`、`scripts/`、`*.test.ts` 属工具/评测/断言，不计入迁移面——v3 审计后核对真实分布，基线从「~298」修正为「产品代码 ~95」，见 §7-D），它们：无统一级别、无域（scope）、无落盘、无采样、无用户可访问面板、无分级开关、无跨进程串联。**这就是「日志系统」要补的洞**——一套贯穿主进程/渲染进程的**运行期诊断日志门面**。

> 第一性判断（D3）：日志的底层价值是「**用户报 bug 时，开发者能在一处拿到一条可复现的诊断链**」；不是「把 print 换成漂亮 API」，更不是「给每条日志加花哨前缀」。
>
> 按 ROI 排序，设计只守**三件高 ROI 的事**（其余一律不做，见 §1 不做清单）：
> 1. **错在哪**（ERROR 级强制带堆栈）——ROI 最高单项，没有就完全没法定位。
> 2. **哪个板块**出问题（scope 分区，对齐业务域，且仅存在于 JSON 字段，不在 msg 拼前缀）——纪律价值（迁移棘轮天然成立）+ 检索价值。
> 3. **卡在哪**（仅 IPC 边界记 callId + 入参/耗时/结果）——只解决唯一真实痛点「渲染发了主进程没收到/崩了」，不做全链路串联。
>
> 反例（ROI 为负，已砍）：全链路 traceId 续链、msg 手拼 `[scope]` 前缀、渲染本地环形缓冲、TRACE 级帧调度。详见 §7。

## 1. 范围与边界（什么做、什么不做）

**做（本系统）：**
- 统一日志门面 `log(scope, level, msg, meta?)`，主进程 + 渲染进程同 API。
- 分级：DEBUG / INFO / WARN / ERROR（4 级，不引入 SILLY/VERBOSE/TRACE——TRACE 级帧调度 ROI 为负，等真有需求再开）。
- 运行时级别控制：默认 `INFO`；`DEBUG` 经启动参数 / 开发者开关开启。
- 落盘：主进程走 `app.getPath("logs")` **真滚动文件**（保留历史段，不清空）；渲染进程经 IPC 上送主进程统一落盘（**渲染层永不直写 Node fs**，守桥契约）。
- 结构化：每行 JSONL（`{ts, level, scope, callId?, msg, meta, err?, pid, thread}`），便于 `jq` 检索。**scope 仅存在于 JSON 字段，不在 msg 拼 `[scope]` 前缀**（机读优先，面板按需渲染给人看）。
- 链路：仅 **IPC 边界**串联——`bridge.ts` 每次 IPC 调用生成 `callId`，随 invoke 上下行透传，主进程 handler 入口记 `meta.callId`。**不做全链路 traceId 续链**（单进程内日志不带 callId，避免噪音）。
- 边界可观测：`bridge` scope 自动记每次 IPC 的入参（redact 后）/ 耗时 / 结果或失败，覆盖绝大多数「卡住」场景，比全链路串联便宜且更直接。
- 用户可访问面板：设置页「诊断」里可查看 / 复制 / 导出**崩溃日志 + 运行日志合并包**（含 `meta.json`：version / platform / 日志级别 / 导出时间），一键发给开发者，消灭「你啥版本」来回问。

**不做（明确排除，避免并行版/功能膨胀 D4，ROI 为负）：**
- 不复刻 per-project 事件日志（那是评测轨迹域，独立、redact、产品语义）。
- 不引入 `pino` / `winston` / `electron-log` 等重依赖——Electron 无浏览器 console 负担，自研轻门面足够，且能守「加新不引重依赖」的极简纪律（R5：选型必经对比，见 §6）。
- 不做远程上报 / 遥测（D4 诚实：Nomi 本地优先，无遥测）。
- 不替代 `console` 在测试里的断言用途（测试 stdout 输出保留，仅产品代码迁移）。
- ❌ 全链路 traceId 续链（AsyncLocalStorage 跨调用串联）——过度工程，真实痛点仅「跨进程断了」，用 IPC callId 已覆盖。
- ❌ msg 手拼 `[scope]` 前缀——与 JSON 字段重复，且不可机读，纯噪音。
- ❌ 渲染层本地环形缓冲兜底——复杂度高、真崩了内存也没了、排障收益小；上送失败只记 stderr 一行即可。
- ❌ TRACE 级帧调度 / 逐 token 埋点——等真有需求再开。

## 2. 设计（D3：为什么 / 机制后果 / 用户体验）

### 2.1 架构位置（守进程三层 `05`）

```
渲染进程 src/                    主进程 electron/
┌──────────────────┐           ┌────────────────────────────┐
│ logger.render     │──IPC──▶  │ logger.main (唯一写者)       │
│ (经 nomiDesktop.  │  log       │  → fs 真滚动文件            │
│  log，bridge 注入  │  +callId   │  → 同时 mirror 到 stderr     │
│  callId)          │           │  → handler 入口记 meta.callId │
└──────────────────┘           └────────────────────────────┘
```

- **渲染层**：只调用 `logger.<level>(scope, msg, meta)`，经 `nomiDesktop.log` IPC 上送；不持 fs、不自己格式化落盘。`bridge.ts` 封装层在**每次 IPC 调用**时生成 `callId` 并随 invoke 上下行透传（不维护 React 上下文 / 全局 trace 状态）。
- **主进程**：`logger.main` 是**全仓唯一文件写者**（类比 `eventLogRepository` 的「唯一写者」纪律），负责级别过滤、滚动、redact、镜像 stderr。无 AsyncLocalStorage 续链——callId 只在 IPC handler 入口那一刻记录，处理链内部日志不带 callId（避免噪音）。
- 复用 `crashLog.ts` 的 `app.getPath("logs")` 目录，不另起目录（P1：复用不新建）。

### 2.2 板块划分（scope 命名直接对齐 `ipcChannels.ts` 业务域）

> scope 与业务域 1:1 对应——排查时"报错在哪个域"和"点哪个功能"直接对上，不造"misc/杂项"scope（P1：单一责任）。

| scope（日志域） | 对应 IPC 域 | 典型日志 |
|---|---|---|
| `lifecycle` | app / window / i18n | 启动、窗口创建/关闭、语言切换 |
| `project` | projects / workspace | 项目创建/读取/诊断/恢复 |
| `asset` | assets / media / video / image / scene3d | 导入、下载、转码、图层拆解 |
| `catalog` | model-catalog / custom-call | 模型/映射增删、ComfyUI 探查 |
| `task` | tasks | 生成任务、文本流、ComfyUI 进度 |
| `agent` | agents | 会话启动、工具确认、流式事件 |
| `export` | exports / production-runs | 导出任务、生产运行 |
| `proxy` | proxy / settings | 代理探测、设置读写 |
| `bridge` | 渲染↔主进程 IPC 通道本身 | IPC 入参/出参/耗时/失败 |
| `ipc` | 跨域通用 | IPC 层通用错误、桥健康度 |

### 2.3 链路设计（仅 IPC 边界 callId，不做全链路串联）

**ROI 判断（核心取舍）**：v2 曾设计全链路 `traceId` + AsyncLocalStorage 续链，把一次用户操作（含内部多步、跨进程）全串起来。重算 ROI 后发现——Nomi 当前单窗口单项目为主，真实痛点**只有一个**：「渲染说发了 IPC，但主进程没反应 / 崩了」。这种场景下你只需要知道「这次调用主进程收没收到」，不需要把业务内部每一步都串成链。

→ **降级方案**：只在 **IPC 边界**做最小串联，不在业务内部扩散。

#### 2.3.1 callId 的生成与透传（守桥契约）

- 渲染层调 `nomiDesktop.xxx(...)` 时，`bridge.ts` 封装**每次调用生成一个 `callId`**（短随机串，如 `c1a2`），随 invoke 的入参一并下传。
- 主进程对应 IPC handler 入口：记一条 `scope:"bridge"` 日志，带 `meta.callId`、redact 后的入参、开始时间戳。
- handler 返回（或抛错）时：再记一条 `scope:"bridge"` 日志，`meta.callId` 相同，带耗时 `ms` 与结果/错误。
- **处理链内部（主进程业务代码）的日志不带 callId**——callId 只在边界有意义，内部带只会稀释信号。

```
渲染进程                                      主进程
┌────────────────────────┐                  ┌──────────────────────────────────┐
│ user click 生成           │                  │ ipcMain.handle(tasks:run)          │
│  bridge 生成 callId=c1a2  │──invoke(c1a2)──▶│  logger.info(bridge,"recv",        │
│  logger.info(task,"提交") │  +入参(redact)    │    {callId:"c1a2",args,ts0})       │
│  (无 callId 字段)          │                  │  ... 业务日志（无 callId）...       │
└────────────────────────┘                  │  logger.info(bridge,"done",        │
                                              │    {callId:"c1a2",ms:1820})         │
                                              └──────────────────────────────────┘
```

#### 2.3.2 排查用法

- **正常**：渲染侧 `tasks:run` 调用后，主进程有同 `callId` 的 `recv` + `done` 两行 → 链路通。
- **静默丢失**（唯一真痛点）：渲染侧记了「提交」但主进程查不到该 `callId` 的 `recv` → 判定 IPC 通道断 / 主进程卡死，直接定位到桥，不用翻全量日志。
- 不做 `jq 'select(.traceId=...)'` 全链拉取——那是过度工程，当前不需要。

#### 2.3.3 为什么不做全链路 traceId

| 维度 | 全链路 traceId | IPC callId（本方案） |
|---|---|---|
| 覆盖痛点 | 含 callId 场景 + 业务内部串联 | 仅「跨进程断了」 |
| 实现成本 | ~100 行（ALStorage + 上下文注入） | ~15 行（bridge 生成 + handler 记两行） |
| 噪音 | 每条日志带 traceId，稀释关键信号 | 仅边界两行带 callId |
| ROI | 低（当前无并发多任务串联刚需） | 高（精准覆盖唯一痛点） |

### 2.4 级别与默认

| level | 默认开 | 用途 | 例 |
|---|---|---|---|
| ERROR | ✅ | 用户可见功能失败 / 未捕获异常 | IPC handler 抛错、供应商调用失败 |
| WARN | ✅ | 可恢复降级 / 配置缺失回退默认 | 模型缺字段回退 |
| INFO | ✅ | 关键生命周期节点 | 窗口创建、项目加载完成 |
| DEBUG | ❌ | 开发期排查（含 IPC 入参/耗时，见 §2.3） | bridge 边界日志 |

- 运行时切换：开发者开关（设置→诊断→日志级别）经 IPC 通知主进程改 `currentLevel`，无需重启。
- 启动参数 `NOMI_LOG_LEVEL=debug` 覆盖默认（CI / 排障用）。
- **ERROR 级强制带错误对象**：`logger.error(scope, msg, error, meta?)`，落盘写入 `err: {name, message, stack}`，否则只看 `msg` 等于没记（v1 漏洞修复）。

### 2.5 落盘格式（JSONL）

```json
{"ts":"2026-08-10T12:00:00.123Z","level":"WARN","scope":"project","pid":1234,"thread":"main","msg":"project load slow","meta":{"ms":1820}}
{"ts":"2026-08-10T12:00:01.000Z","level":"INFO","scope":"bridge","callId":"c1a2","pid":1234,"thread":"main","msg":"ipc recv","meta":{"channel":"tasks:run","args":{"projectId":"p1"},"ts0":"...}}
{"ts":"2026-08-10T12:00:01.456Z","level":"ERROR","scope":"task","callId":"c1a2","pid":1234,"thread":"main","msg":"vendor call failed","err":{"name":"FetchError","message":"timeout","stack":"..."},"meta":{"vendor":"replicate","model":"sk-..."}}
{"ts":"2026-08-10T12:00:02.820Z","level":"INFO","scope":"bridge","callId":"c1a2","pid":1234,"thread":"main","msg":"ipc done","meta":{"ms":1820}}
```

> scope 只在 JSON 字段，不在 msg 拼前缀；`callId` 仅 IPC 边界两行（recv/done）带，错误行若属同次调用可带（如上 `vendor call failed` 带 `c1a2` 便于对账），业务内部日志不带。

- **真滚动（v1 根因修复）**：单段 ≤2MB 时滚出 `nomi.1.log` / `nomi.2.log` …（保留最近 5 段，约 10MB 上限），**绝不清空当前文件**。日志是排障不是审计，但"排查中途把日志抹掉"直接摧毁目标。
- 复用 `crashLog` 的 `MAX_BYTES` 常量（2MB），但**改其"超限即清空"策略为滚动**——`crashLog` 的清空策略仅适用于"崩溃即终态"语义，运行日志不适用。运行日志滚动逻辑独立实现于 `logger.ts`，不污染 `crashLog`（不动项见 §3.2）。
- redact：落盘前跑 `eventLogRepository` 同款 `redactDeep`（密钥/API key 不进日志，评测安全铁律延续）。**⚠️ v3 修正（§7-E）**：运行日志是通用日志，不能只依赖 catalog secrets 清单——`meta` 里带 `args` 的 IPC 入参先做**保守默认层**（`redactDeep` 已含敏感字段名 `api_key/authorization/token/secret/password/x-api-key` + `sk-`/`Bearer` 形态兜底），再叠加 secrets 清单；两层的交集 = 最终脱敏，杜绝「入参记录」本身成为密钥泄露口。
- 失败策略：**旁路观察**——任何 IO 失败只 swallow，绝不打断产品主流程（与 `eventLogRepository` 注释精神一致）。
- 时间：`ts` 统一 `toISOString()`（UTC），与 `crashLog` 一致；排查时明确"日志一律 UTC"，避免和本地崩溃时间混淆（v1 漏洞 #6 修复）。

### 2.6 渲染层上送的丢失处理（ROI 降级）

渲染层经 IPC 上送主进程落盘。v2 曾设计「渲染本地环形缓冲 200 条兜底」，重算 ROI 后砍掉——复杂度高、真崩了内存缓冲也没了、排障收益小。

- 上送走 `ipcRenderer.send`（fire-and-forget），**不阻塞渲染主线程**。
- 上送失败（通道拥堵 / 主进程卡死）记一行 `logger.error('bridge', 'log flush failed', err)` 到 **stderr**（至少开发者控制台可见），不维护内存缓冲。
- 边界可观测已靠 §2.3 的 `callId` 覆盖「跨进程断了」痛点——若主进程查不到某 `callId` 的 `recv`，即知上送丢失，无需渲染侧缓冲佐证。

### 2.7 用户面板（D1：从用户摩擦出发）

用户报 bug 时的摩擦：「我截图给你，但你还要我翻系统目录找日志」。→ 设置页「诊断」提供：
- **合并预览**：同时呈现 `nomi-crash.log`（崩溃） + `nomi.log`（运行）最近各 N 行（v1 漏洞 #2 修复——不再割裂两份）。**⚠️ v3 修正（§7-E）**：两份日志格式不同（crash 是 `[ts] [scope] msg`，运行是 JSONL）——预览统一**按行内时间戳解析后按时间排序**再展示，不直接拼两个文件，避免格式错乱。
- 「复制」「导出 .zip」，包内除崩溃 + 运行日志外，**必含 `meta.json`**：`{version, platform, arch, logLevel, exportedAt, appPath}`。零成本消灭「你啥版本 / 啥系统」来回问（ROI 极高）。
- 不强制、不常驻弹窗（D4：不污染体验）。

## 3. 落地计划（R4：范围 / 不动项 / 回滚 / 验收）

### 3.1 文件与改动

| 文件 | 动作 | 说明 |
|---|---|---|
| `electron/logger.ts`（新） | 建 | 主进程 logger 门面 + 真滚动 + redact + 级别；`nomiDesktop.log` handler；无 AsyncLocalStorage |
| `electron/preload.ts` | 改 | 暴露 `nomiDesktop.log(level, scope, msg, meta)`；**把 `ipcRenderer.invoke` 收进统一 `call` helper**：每次调用生成 `callId` 随入参透传 + 主进程 handler 入口/返回记 `scope:bridge`（recv/done，带 `callId` + redact 入参 + 耗时）。⚠️ v3 修正：`bridge.ts`（`src/desktop/`）只是 `DesktopBridge` 的**类型定义 + getDesktopBridge()**，不是调用封装——真正的调用点在 `preload.ts` 的 `ipcRenderer.invoke`，故 callId 注入落在这里（最小改动，见 §7-E） |
| `src/utils/logger.ts`（新） | 建 | 渲染层门面，调 `nomiDesktop.log`（fire-and-forget，无内存缓冲） |
| `src/workbench/settings/DiagnosticsSection.tsx`（新，并入设置「通用」） | 建 | 日志级别开关 + 崩溃/运行合并预览/导出（含 `meta.json`） |
| 产品代码 ~95 处 `console.*` | 迁 | **逐步替换**为 `logger.*`，按 §2.2 scope 分批（P1：加新必删旧，无并行版；`evals/`、`scripts/`、`*.test.ts` 不迁移） |

> **`scope:"bridge"` 自动记录的触发范围（v3 修正，防噪音淹没）**：只对 **`invoke`（请求-响应，有完成语义）** 自动记 recv/done；**`send`（fire-and-forget 单向事件）不自动记**——`browser` 域 view 操作、`comfyui:progress`、`tasks:text:event` 等高频事件若每次 invoke 都记两行，DEBUG 下会刷屏。且 `invoke` 也只记**慢调用（>500ms）或失败**，正常快速调用不记，避免日志膨胀（见 §7-E）。

### 3.2 不动项（不碰）

- `electron/crashLog.ts`：崩溃域独立，本系统只复用其目录与 `MAX_BYTES` 常量，**不合并逻辑、不改其清空策略**（运行日志滚动独立实现）。
- `electron/events/eventLogRepository.ts`：评测轨迹域，完全不动。
- 测试文件里的 `console.*`：保留（断言/输出用途），仅迁移产品代码。

### 3.3 回滚

- 日志门面纯增量、旁路；任一模块迁移出错，回退该模块 `logger.* → console.*` 即可，无数据迁移风险（日志文件非结构化状态）。
- 引入开关：若上送 IPC 在极端场景抖动，主进程可降级为「只 stderr 不落盘」；渲染侧上送失败记 stderr 一行（无内存缓冲兜底，见 §2.6 ROI 说明）。

### 3.4 验收门（R11 五门前）

- `lint:ci`：`console.*` 在产品代码的新增数为 0（用 `grep` 棘轮：基线 `electron/`+`src/` 非 test 非 scripts 产品代码 ~95 → 只降不升）。
- `check:tokens` / `check:i18n`：面板文案走 i18n，无硬编码。
- `typecheck` / `test` / `build`：全绿。
- 真机走查（R13）：
  1. 开 DEBUG 级别 → 触发一次项目加载 → 设置页能预览到对应 `scope:"project"` 日志行。
  2. **边界验证**：点一次"生成" → 导出日志 → 主进程有同 `callId` 的 `bridge` recv + done 两行；制造 IPC 静默丢失场景 → 渲染侧有「提交」但主进程无该 `callId` 的 recv，可据此定位桥问题。
  3. **ERROR 验证**：制造一次 IPC 抛错 → 导出日志 → 对应行带 `err.stack` 非空。
  4. **导出包验证**：导出 .zip → 内含 `meta.json` 且 version/platform 正确。

## 4. 删旧路径（P1：加新必删旧，无并行版）

`console.log/error/warn/info` 在引入 `logger` 后**属于旧实现**，必须随迁移删除，不允许「留着 console 当 fallback」。分批顺序（按风险从低到高，且按 §2.2 scope 对齐）：

1. 主进程 `main.ts` 现有 `[nomi:desktop]` 系列 → 先迁（已有 scope 命名习惯，直接对齐 `lifecycle`）。
2. `electron/` 其余模块 → 按 §2.2 表逐 scope 迁移（catalog/task/asset/export…）。
3. `src/` 渲染层（经 bridge，自动带 callId，业务内部不带）。
4. 每批迁完即跑 `lint:ci` 确认 `console.*` 计数下降。

> 棘轮纪律：新增文件禁止再写 `console.*`（门岗加 `no-console` 规则，仅产品代码；测试/调试临时 console 走显式豁免注释标记）。

> **落地进度（2026-08-10 首版落地）**：`logger.ts`（真滚动/双层 redact/级别过滤）+ `logIpc.ts` + preload 暴露 `log`/`diagnostics` + 渲染门面 `src/utils/logger.ts` + 设置「通用·诊断」面板（级别开关/合并预览/导出）已全部实现并跑通。**electron/ 产品代码 console 已基本清零**（仅剩 `mcpStdioServer`/`browserViewBridges` 两个刻意传输 + `main.ts` console-message 转发 + `crashLog`/`eventLogRepository` 豁免域 + 测试文件）。渲染侧迁移了 `NomiStudioApp`/`ErrorBoundary`/`chunkBoundary`/`startupDiagnostics`/`videoPlaybackDiagnostics`（app 壳/崩溃/启动/播放——最高价值诊断面），其余 ~12 个低频 UI 文件（scene3d/AssetLibraryPanel/export 等）属下一批渐进迁移。测试全绿：electron 1785（0 失败）、渲染 2262（0 失败）。
>
> ⚠️ **已发现的架构性豁免（v4.1 根因修复后撤销）**：`logger.ts` 曾 import `electron` 的 `app`，导致 `systemProxy`/`vendorBaseFallback`/`browserViewBridges`/`videoImportNormalize`/`buildAiSdkModel` 等「纯 Node 单测」模块无法安全迁移（会破坏其纯 Node 测试）。**v4.1 根因修复（P2）**：`logger.ts` **彻底不 import electron**——日志目录/版本/secrets 清单全部由主进程 `main.ts` 启动时经 `initLogger()` 注入，未注入时静默退化为 stderr。→ 纯 Node 模块现在可安全 import `logger`（不触发 electron 运行时），上述豁免撤销，全部可迁移。仅剩两处**传输性保留**：`main.ts` 的 `console-message` 转发（渲染层 stdout 镜像）与 `crashLog`/`eventLogRepository`（崩溃域 + 评测域，设计 §3.2 不动项）。

## 5. 选型说明（R5：碰三方库先查；引入新框架先对比）

评估是否用现成库 vs 自研：

| 方案 | 用户看到 | 代价 | 结论 |
|---|---|---|---|
| `electron-log` | 开箱即用的主+渲日志、transports | 额外依赖 ~30KB；API 与现有 `crashLog`/`eventLogRepository` 风格不统一；遥测倾向 | **否**（D4 极简 + 本地优先，不引遥测倾向库） |
| `pino` / `winston` | 工业级、插件多 | 重；浏览器侧需额外适配；过度工程 | **否** |
| **自研轻门面**（本方案） | 统一 API、复用现有落盘/redact 设施、零新依赖、IPC 边界 callId | 需自己写 ~120 行（比全链路 traceId 省 ~80 行） | **是**（P1 复用、D4 极简、守桥契约、ROI 优先） |

自研不违反 R5「查官方文档」——R5 针对「第三方库能力/新旧判断」；本方案结论正是「不引入第三方库」，依据是对现役库的对比评估（上表），而非凭记忆。
