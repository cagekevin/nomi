# 07 · 节点组件契约表（2026-08-10）

> 配套：`06-事件总线设计`（跨层通信单一真相）的同系文档。本文把「生成画布节点系统」的契约钉死，让后来者一眼看懂**一个节点 kind 由哪些字段定义、组件收到什么、怎么执行、加新 kind 改哪几处**。
> 代码入口图见 `src/workbench/generationCanvas/ENTRY.md`（112 文件地图，搜符号前先定位）。

---

## 0. 一句话：节点系统是「深模块」的好样本

Nomi 的 16 个节点 kind **不各写一套组件**，而是共用一个外壳 `BaseGenerationNode.tsx` + `resolveNodeRenderKind(node)` 分发到专属 card body（`CharacterCardNode.tsx` / `SceneCardNode.tsx` …）。新增一个 kind 的「渲染差异」只写在 body 组件里，**外壳/连线/手势/尺寸/状态机全不动**。

这正是你要的「深模块 = 改哪只动哪」：节点差异被封装在 `renderKind` 分发背后，调用方（画布/store/runner）感知不到内部 kind 数量。本文把这个契约显式化，避免它靠「读 BaseGenerationNode 才知道」。

---

## 1. 三层契约总览

| 层 | 契约定义位置 | 管什么 | 消费方 |
|---|---|---|---|
| **① 插件注册契约** | `nodes/registry.ts` `GenerationNodePluginDefinition` | 声明一个 kind 的元数据（尺寸/图标/分类/能否生成/能否 agent 建） | `renderRegistry.tsx` · `model/generationNodeKinds.ts` |
| **② 渲染组件契约** | `nodes/registry.ts` `GenerationNodeRenderProps` | 组件运行时收到的 props | 所有 `BaseGenerationNode` + card body |
| **③ 执行契约** | `registry.executionKind` + `runner/` | 节点怎么发任务、出什么结果类型 | `runner/generationNodeExecutor.ts` · `generationRunController.ts` |

三层都集中在 `nodes/registry.ts` + `model/generationCanvasTypes.ts`，**是节点域的单一真相源**（类比 `ipcChannels.ts` 是 IPC 的单一真相源）。

## 2. 契约字段定义（逐项）

### 2.1 插件注册契约 `GenerationNodePluginDefinition`（`registry.ts:30-44`）

| 字段 | 类型 | 含义 | 谁读 |
|---|---|---|---|
| `kind` | `string` | 节点唯一标识（如 `'character'`）。**全系统主键** | 所有层 |
| `label` / `menuLabel` | `string` | 菜单/标题显示名（已被 i18n 覆盖，`renderRegistry.tsx:68-69`） | 菜单 |
| `component` | `() => Promise<{default: GenerationNodeComponent}>` | **懒加载**组件（动态 import，见 `loadBaseGenerationNode`） | `renderRegistry.tsx` |
| `icon` | `GenerationNodeIconKey` | 图标 key，映射到 `NODE_ICONS`（`renderRegistry.tsx:36-50`） | 菜单/节点头 |
| `defaultSize` | `{width,height}` | **尺寸单一真相源**（见 §4）。无 `node.size` 时回退此值 | `model/generationNodeKinds.ts:25` |
| `catalogKind` | `BillingModelKind` | 计费/目录分类（text/image/video/audio/model3d） | catalog/计费 |
| `executionKind` | `'image'\|'video'\|'text'\|'audio'\|'model3d'`? | **执行契约**：有值=生成节点，无值=纯参考/资产 | `runner/` · `isImageLike...`(`generationNodeKinds.ts:98`) |
| `quickAdd` | `boolean?` | 快捷添加面板是否出现（默认 true） | 添加面板 |
| `agentCreatable` | `boolean?` | agent 工具能否建此 kind（默认 false） | `agent/` |
| `providesImageReference` | `boolean?` | 能否作为图像参考被连线（角色/场景/图/素材=true） | 连线/参考 |
| `defaultTitle` / `promptPlaceholder` | `string?` | 默认标题 / 提示词占位（i18n 覆盖） | 节点头/composer |

### 2.2 渲染组件契约 `GenerationNodeRenderProps`（`registry.ts:4-11`）

```ts
type GenerationNodeRenderProps<TNode = unknown> = {
  node: TNode            // 完整节点数据（GenerationCanvasNode）
  selected: boolean      // 是否选中
  readOnly?: boolean     // 只读（如历史快照回放）
  focusFlash?: boolean   // 聚焦高亮闪一下
  appear?: boolean       // 新落点一次性弹入动画（已有节点不传，防齐闪）
}
```

> **关键**：组件拿到的只有这 5 个 props，**不直接碰 store / IPC / 文件**。所有副作用走 `BaseGenerationNode` 外壳统一处理（选中态、手势、连线、状态机）。这是「深模块」的体现——body 组件极浅，复杂度在外壳。

### 2.3 执行契约（隐式，靠 `executionKind` 驱动）

`runner/generationNodeExecutor.ts` 按 `executionKind` 分流到对应任务构造（`catalogTask*`），结果写回 `GenerationNodeResult`（`generationCanvasTypes.ts:69-87`）。无 `executionKind` 的 kind（`shot`/`output`/`asset`/`whiteboard`）**不进执行流**，只作内容/参考。

## 4. 尺寸单一真相源（重要坑位）

节点尺寸**只有一个函数说了算**：`getNodeSize(node)`（`model/generationNodeKinds.ts:53-55`）——`node.size ?? DEFAULT_NODE_SIZE[kind] ?? 兜底`。

- 所有几何子系统（虚拟化/fitView/连线命中/框选/minimap/分组框/碰撞避让）**必须**经此函数取尺寸，不许内联 `||300/220` 或裸 `320×360`（注释 `generationNodeKinds.ts:48-52` 明说那是「第二份真相源」bug 来源：同一节点在不同子系统被算成不同大小 → 框选选不中）。
- 落点间距用 `getGenerationNodeFootprintSize(kind, size)`（`+NODE_RENDER_SAFETY=64`），吸收「渲染 > 名义」的增量，防重叠。

## 5. 加一个新节点 kind 要改哪几处（呼应「改一处动多处」）

这是本文对开发者的核心价值——把「加 kind」的改动面钉死，**理想情况下只动 1-2 处**：

| 改动 | 文件 | 必改？ |
|---|---|---|
| 在 `GENERATION_NODE_PLUGINS` 加一个定义对象 | `nodes/registry.ts:57` | ✅ 唯一必改（声明契约） |
| i18n 加 `runtime.nodeRegistry.<kind>.{menu,title,placeholder}` | i18n 资源 | ✅ 若需中文/英文菜单 |
| 若需专属渲染 body | `nodes/render/*.tsx` + `resolveRenderKind.ts` 加分发 | 仅当现有外壳不够 |
| 若需生成 | `runner/` 加 `catalogTask<Kind>` + 在 executor 分流 | 仅当有 `executionKind` |
| 分类映射 | `getDefaultCategoryForNodeKind`（`generationNodeKinds.ts:31`） | 仅当新分类 |

**好消息**：外壳（`BaseGenerationNode`）、连线、手势、尺寸、状态机、撤销重做 **全不用动**——这就是深模块「改哪只动哪」。

**反模式警示**（避免新债）：
- ❌ 别为某个 kind 写平行外壳（旧 `WhiteboardCardNode` 已删，见 `registry.ts:216-217` 注释）——复用 `BaseGenerationNode` + body 分发。
- ❌ 别在 body 里直接调 store/IPC——副作用走外壳。
- ❌ 别在几何子系统内联尺寸常量——走 `getNodeSize`。

## 6. 与「深模块 / 事件总线」的关系

- 节点系统已是**深模块范本**：16 kind 共用外壳，差异藏在 `renderKind` 分发后。
- 节点结果回流前端靠**事件**（如 `nomi:tasks:text:event` / `nomi:exports:event`，见 `preload.ts:324,303`）——这正是 `06-事件总线设计` §1 机制 A 的实例。节点生成完成 → 后端 publish 事件 → 前端 store 更新。**节点域和事件总线是上下游**，统一事件真相后能进一步收敛节点结果回流的散落。
