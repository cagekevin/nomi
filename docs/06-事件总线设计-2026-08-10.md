# 06 · 事件总线设计（探索 / 2026-08-10）

> 状态：**探索文档**，未落地。本文先厘清「Nomi 现在事件怎么流」，再给出「该长什么样」的目标形态与取舍，**不写代码**。
> 配套：本文是 `02-开发上手` §3.5「改一处动多处」的第四根源，也是 `docs/plans/2026-08-10-decouple-ipc-runtime.md`（A: IPC 常量化）的同源问题——两者都源于「跨层通信靠裸字符串/碎片机制」。

---

## 0. 一句话结论（先给判断）

Nomi **没有统一事件总线**，而是 **4 套各写各的事件机制** 散落在前后端。这是「改一处动多处」的第四根源——比 IPC 裸字符串更隐蔽，因为它连统一的名字都没有。

正确方向不是「新造一个全局事件总线」（那是反模式 + 违反 P1 加新必删旧），而是 **把 4 套碎片收敛成「受控、分域、类型化」的单一事件真相**，与 IPC 桥同层、共用命名纪律。

---

## 1. 现状：4 套事件机制全景（都有真实位置）

### 机制 A · 后端直接 `webContents.send`（裸字符串推送）

后端不经任何总线，直接往窗口推裸 channel 字符串：

| channel | 位置 | 场景 |
|---|---|---|
| `nomi:assets:updated` | `electron/assets/assetEvents.ts:11` | 素材写入后广播所有窗口刷新 |
| `nomi:window:maximized` | `electron/main.ts:308-309` | 窗口最大化状态 |
| `nomi:window:close-request` | `electron/windowCloseConfirmation.ts:45` | 关闭确认 |
| `nomi:screenshot:captured/denied/failed` | `electron/screenshot/screenshotHotkey.ts:171-218` | 截图结果 |
| `nomi:production-deep-link` | `electron/productionRun/productionRunDesktopLifecycle.ts:30` | 生产深链 |
| `nomi:tasks:comfyui:progress` | `electron/comfyuiProgressSocket.ts:9` | ComfyUI 进度（注释明说「镜像 textStreamIpc 单向事件范式」）|

**问题**：裸字符串、无类型、无中心注册表；每个新事件要手写 `BrowserWindow.getAllWindows()` 循环（见 `assetEvents.ts:8-13`）；前端订阅方在 `preload.ts` 里逐个 `ipcRenderer.on(...)`（见 §3），新增/改名要手工对齐。

### 机制 B · 前端内部 `window.dispatchEvent(new CustomEvent(...))`

渲染进程内各模块自己发 DOM CustomEvent，常量各写各的：

| 事件名 | 位置 | 场景 |
|---|---|---|
| `nomi-open-browser` | `src/workbench/WorkbenchShell.tsx:123` 等 3 处 | 打开浏览器画布 |
| `nomi-open-model-catalog` | `src/workbench/ai/NoTextModelRecoveryCard.tsx:57` 等 6 处 | 打开模型目录 |
| `nomi-model-catalog-changed` | `src/workbench/ai/NoTextModelRecoveryCard.tsx:65` | 模型目录变更 |
| `nomi-focus-generation-node` | `src/workbench/sidebar/CategoryTree.tsx:188` | 聚焦画布节点 |
| `MODEL_REFRESH_EVENT` | `src/config/modelCatalogCache.ts:70` | 模型刷新 |
| `DESKTOP_ACTIVE_PROJECT_CHANGED_EVENT` | `src/desktop/activeProject.ts:16` | 当前项目切换 |
| `PROMPT_EXTRACTION_FEEDBACK_EVENT` | `src/ui/browser/prompt/browserPromptExtractionRunner.ts:126` | 提示词抽取反馈 |

共 **24 处** `window.dispatchEvent(new CustomEvent(...))`，事件名有 `nomi:` 前缀的、有裸名的、有常量抽出的——**命名纪律不统一**。

### 机制 C · Zustand store 当事件用

`workbenchStore.ts` / `generationCanvasStore.ts` / `generationQueueStore.ts` 等 **81 处** 用 `subscribe` / `set` 做事件订阅。状态即事件，耦合进 store，无独立事件语义。**这部分不应强行改成总线**——它是「状态」不是「通知」，见 §5 反模式。

### 机制 D · Node `EventEmitter` 流式

`textStreamIpc.ts` / `comfyuiProgressSocket.ts` 用 EventEmitter 做模型流式输出。**仅限流式场景，不通用**，迁到总线时可作为「流式事件」特例保留。

## 2. 前端订阅方现状（preload 里逐个 on）

后端 A 类事件在前端由 `electron/preload.ts` 逐个 `ipcRenderer.on(...)` 暴露（共 22+ 处）：

```
electron/preload.ts:7   ipcRenderer.on("nomi:production-deep-link", ...)
electron/preload.ts:48  ipcRenderer.on("nomi:window:close-request", ...)
electron/preload.ts:140 ipcRenderer.on("nomi:assets:updated", ...)
electron/preload.ts:303 ipcRenderer.on("nomi:exports:event", ...)
electron/preload.ts:335 ipcRenderer.on("nomi:tasks:comfyui:progress", ...)
... (共 22+)
```

**问题**：和 IPC handler 一样——channel 裸字符串、`main.ts` 发 / `preload.ts` 收 / 业务组件用 三层手工对齐，编译器不查。

---

## 3. 为什么这是「改一处动多处」的第四根源

把今天探索出的四个根源并列，你会看清它们的同构性：

| # | 根源 | 散落层 | 类型安全 | 本质 |
|---|---|---|---|---|
| 1 | IPC channel 裸字符串 | main / preload / bridge / 前端 四层 | ❌ | 跨层请求靠字符串 |
| 2 | `runtime.ts` 百货层 | 36 文件反向依赖 | ⚠️ 方向乱 | 类型集中但依赖倒挂 |
| 3 | 供应商适配多文件 | catalog/ 131 文件 | ✅ | 诚实代价，**不动** |
| **4** | **事件机制碎片化** | **A 后端 send / B 前端 CustomEvent / C Zustand / D EventEmitter** | **❌** | **跨层通知靠 4 套碎片** |

根因同构：**跨层通信没有单一真相**。请求侧（#1）和通知侧（#4）是同一道题的两面——都该有「类型化、分域、编译器可查」的中心注册表。

> 注：`assetEvents.ts:10` 的注释已经悟到了正确原理——「写入层是唯一咽喉，挂在这里整类导入路径免费获得回流」——但只做了一半：它用的是裸 `webContents.send("nomi:assets:updated", ...)`（遍历所有窗口推送），没升级成总线，所以仍是碎片之一。

## 4. 目标形态：受控、分域、类型化事件总线

### 4.1 设计原则（先定纪律，再定形状）

1. **单一真相**：所有跨层事件名集中在 `electron/shared/eventChannels.ts`（与 IPC 解耦计划里的 `ipcChannels.ts` 同源、同命名纪律 `nomi:<domain>:<name>`；两者均属 `docs/plans/2026-08-10-decouple-ipc-runtime.md` 的**待建**目标，尚未落地）。
2. **分域隔离**：事件按域分区（`assets.*` / `window.*` / `screenshot.*` / `production.*` / `canvas.*` / `tasks.*` / `model.*`），每个域只暴露自己域的事件，禁止跨域发任意事件。
3. **类型化负载**：`EventMap` 类型表，`emit("assets:updated", payload)` 编译器校验 payload 形状；订阅方 `on("assets:updated", cb)` 自动推断。
4. **单向优先**：默认 **后端 → 前端推送**。前端 → 后端一律走 IPC 请求响应（不抢事件通道）。双向与否见 §4.4 取舍表。
5. **fire-and-forget 与请求响应分离**：事件 = 通知（无返回值）；要返回值用 IPC。绝不混用。

### 4.2 形态草图（不写实现，只定接口形状）

```
electron/shared/eventChannels.ts     // EventMap 类型表 + channel 常量（单一真相）
electron/shared/eventBus.ts          // 后端发布：publish(domain, name, payload) → 遍历窗口 webContents.send
src/desktop/eventBus.ts              // 前端订阅：on(domain, name, cb) / off(...)（经 preload 桥）
electron/preload.ts                  // 桥里一次性转发所有事件，不再逐个 ipcRenderer.on
```

对比现状：
- 现在：加一个事件 = 改 `main.ts`(发) + `preload.ts`(收，22 行里再加一行) + 业务组件(用)。
- 目标：加一个事件 = 只在 `eventChannels.ts` 的 `EventMap` 加一行类型；`preload.ts` 桥自动转发，业务组件 `on(...)` 编译器补全。

### 4.3 与深模块的关系（回应你的核心诉求）

你要的「深模块 = 改哪只动哪」，事件总线是**最该先建的基础设施**：

- 现状：新增一个「素材导入入口」（捕捞/拖拽/上传/agent/MCP），每个入口都要自己 `broadcastAssetsUpdated` 或在某处手写回流 → 漏一个就少刷新（这正是 `assetEvents.ts:10` 的注释想消灭的）。
- 目标：写入层挂一次总线订阅，所有导入入口免费获得回流。**副作用收敛到单一咽喉 = 改一处只动一处**。

### 4.4 关键取舍：要不要双向？（待你拍板）

| 方案 | 说明 | 用户体感收益 | 风险 / 成本 |
|---|---|---|---|
| **单向（后端→前端）** | 只推送；前端→后端一律 IPC | 解决「改一处动多处」推送侧；最安全 | 前端内部 B 类 CustomEvent 碎片仍在（需另立前端内部总线，见下） |
| **双向但禁请求响应** | 前端也能 `publish` 给 main（如画布交互通知），但禁用事件做请求响应 | 统一前端→后端通知通道，少一套机制 | 需约束「事件 vs IPC」边界，否则退化成全局总线 |
| **含前端内部总线** | 把 B 类 DOM CustomEvent 也收进同一 `EventMap` 封装 | 全链路一套纪律，最完整 | 迁移成本最高（24 处 CustomEvent + 命名统一） |

**我的真判断（D5）**：先落 **单向**（后端→前端），它直接消灭最痛的 A 类裸 `webContents.send` 和 preload 22 行碎片，且不与 IPC 抢语义。B 类前端 CustomEvent 是「前端内部通知」，可第二步用轻量 `EventMap` 封装收口（不跨进程，不涉及 preload），不必和后端总线强绑。C/D 不动。

## 5. 迁移路径（按风险排序）

| 批次 | 迁什么 | 从 → 到 | 风险 |
|---|---|---|---|
| 1 | A 类裸 `webContents.send`（`assetEvents.ts`/`main.ts:308`/`screenshotHotkey.ts`/`productionRunDesktopLifecycle.ts`） | 裸字符串 → `eventBus.publish` + `EventMap` | 低 |
| 2 | `preload.ts` 22 行 `ipcRenderer.on` | 逐个 → 桥自动转发 | 低 |
| 3 | B 类前端 CustomEvent（24 处） | 裸 `dispatchEvent` → 前端 `eventBus` 封装（仅前端内） | 中 |
| — | C 类 Zustand `subscribe` | **不动**（状态非通知） | — |
| — | D 类 EventEmitter 流式 | **不动**（流式特例，可挂总线「流式事件」标签） | — |

**回滚**：每批独立可回滚；channel 常量与 `EventMap` 同 commit 引入，旧裸字符串在同批删除（P1 加新删旧，无并行版）。

## 6. 反模式警示（写进纪律，避免新债）

1. ❌ **禁止全局任意事件**：事件必须分域、集中注册，任何人不能发未登记的事件。
2. ❌ **禁止事件里传大对象**：payload 只放 id / 轻量状态，重数据走 IPC 拉取。
3. ❌ **禁止用事件做请求响应**：要返回值 = IPC；事件 = 通知。
4. ❌ **禁止为「文件少」合并 catalog 供应商适配**（重申 P1）：那是声明驱动多供应商的诚实代价。
5. ❌ **禁止新造第二套事件机制**：新增跨层通知必须走 `eventBus`，旧机制在迁移批次里删除。
