# 04 · Nomi 第三方 API 接入机制探索

> 探索文档（developer-facing）。目标：把「Nomi 怎么接第三方 API」「所有请求头从哪来」「生图 / 视频 / 聊天三条机制的调用链」讲清楚。
> 用户视角的上手流程见 `docs/provider-integration.md`（那份讲"怎么填表单"），本篇讲"表单背后是怎么跑的"。
> 配套：`provider-integration.md`(用户视角) · `03-上手指南-2026-08-10.md`(环境/运行) · `11-工程纪律详解-2026-08-10.md`(R1–R15)。
>
> **踩坑实录（本篇最重要的部分，写在最前）**：本地自建 / 私有中转网关**不能走"手动录入 + 填表验证"那条路**，会在"官方文档发现"阶段就整批失败（见 §1.6）。正确走法是**写一份独立 curated vendor 档案（`lovartVendor.ts` + seed 注册 + `KNOWN_VENDORS` 卡），复用协议兼容的内置 mapping 形状**（见 §1.5）。**不要复用 APIMart 卡**——apimart 是付费核心通道、动了影响正常付费用户（2026-08-10 用户明确要求），本地网关必须独立成家。这条岔路之前文档没讲清，导致接本地网关时反复碰壁。

## 0. 一句话心智模型

Nomi 不写死任何供应商。一切第三方调用都跑在一条**数据驱动的管线**上：

```
catalog（数据：vendor / model / mapping）
        │
        ▼
profileHttpRequest / buildHttpRequest   ← 模板引擎 + 鉴权 + URL 拼接（单一真相源）
        │
        ▼
vendorHttp（requestJson / requestMultipart） ← 实际发 HTTP
        │
        ▼
runtime.runTask（编排：解析映射 → 组装请求体 → 发 → 落资产 / 轮询）
```

- **供应商（vendor）** = 一个 base URL + 鉴权方式 + 可选自定义头。
- **模型（model）** = 挂在某个 vendor 下的一个 `modelKey`（如 `gpt-4o`、`seedream-3.0`）。
- **映射（mapping）** = 一组 HTTP 操作模板（请求体 / 响应解析路径），把"生图 / 视频 / 聊天"这类能力翻译成某供应商的真实 API 调用。

**关键设计（P1 单一真相源 / P4 通用第一）**：文本走 AI SDK，图像/视频走自建管线，但两条路最终共用同一套 `requestPipeline` 的请求构建逻辑（见 §2），所以"向导里测试通过的请求"和"生产里真打的请求"是同一个编译器产物，不会漂移。

## 1. 怎么添加第三方 API

这是整个接入机制里**最容易踩坑**的一节。先讲清楚 Nomi 有**两条本质不同的接入路径**，然后讲本地/私有网关该走哪条。

### 1.1 两条路径的本质区别（必读）

| 维度 | 路径 A：手动录入 + 适配器自动编译 | 路径 B：内置/市场供应商 seed（填 key 即用） |
|---|---|---|
| 入口 UI | 「添加一个 AI 模型」表单（中转站/官方厂商/接入地址/Key） | 供应商卡（如 APIMart / Kie / 火山）「填 key 解锁」 |
| 后端主进程入口 | `adapterStart` → `ProviderAdapterService.process()`（`providerAdapter/service.ts`） | `upsertVendorApiKey` / `upsertVendor`（`catalog/catalogStore.ts`） |
| **是否需要官方文档** | **是，强依赖**。第一步 `discovering_docs` 去供应商站点抓文档（§1.6） | **否**。mapping 已随 seed 预置，不抓文档 |
| 验证流程 | `AdapterVerificationScreen`：逐个模型验证 chat/生图/视频 mode | `VendorOnboardCard`：仅 `GET /models` 探活（声明 `connectionTest:'models'` 的家） |
| 本地/私有网关能不能走 | **不能**（localhost 无公开文档站 → 整批 failed） | **能**（seed 自带 mapping，只改 baseUrl） |
| 适用对象 | 有公开 API 文档的云厂商（OpenAI / Anthropic / 各模型官网） | 内置支持的厂商 + 协议兼容的本地网关 |

> **结论（D1 outside-in）**：用户填表单时以为"填地址+key 就行"，但路径 A 背后是"自动读官方文档 → 编译适配器"，对**没有文档站的本地网关是死路**。本地/私有中转（如你自己跑的 `apimart-gateway`）必须走**路径 B**。

### 1.2 路径 B：用户手动录入（手动建 vendor，但含义是"建一个空壳等 seed 接管"）

renderer 表单收集（仅当走路径 A 时用）：
- `baseUrl`（接入地址，如 `https://api.modelarts.com/v1`，**路径 A 下必须带 `/v1` 且必须是公开站点**）
- `apiKey`（加密存储）
- `providerKind`（AI SDK provider 种类：`openai` / `anthropic` / `azure` / `deepseek` / `google` / `moonshot` / `openai-compatible` 等）
- `authType`（`none` / `bearer` / `x-api-key` / `query`）
- `meta.extraHeaders`（键值对 → 中转/网关切额外头，见 §3）
- 模型列表（modelKey + kind）

录入后落到 `catalogCommit.ts` 的 `commitManualOpenAiCompatibleModels` / `upsertModelCatalogVendor` 等函数，写回 `catalogStore`。

### 1.3 路径 B（续）：curated 供应商档案（"候选供应商"）

> **更正（2026-08-10 审计）**：本节原稿写的是「`catalog/market/*.json` + `catalogMarket.ts` + `applyMarketVendor`」的「模型市场」机制，**该机制当前不存在**——`catalog/` 下没有 `market/` 子目录，也没有 `catalogMarket.ts`/`applyMarketVendor`。实际的「候选/内置供应商」档案是**直接写在 `catalog/*.ts` 里的 curated 源码**（如 `catalog/apimartVendor.ts`、`catalog/kieSeedream.ts`、`catalog/seedBuiltins.ts` 里的 `ensureBuiltinModelSeeds`），由官方维护、随代码分发，不是 JSON 市场文件。

**真实机制**：每个支持「填 key 即用」的供应商，其 `vendor` + `model` + `mappings`（HTTP 操作模板）都是一份 curated TypeScript 档案，常驻 `electron/catalog/*.ts`：

- `seedBuiltins.ts` 的 `ensureBuiltinModelSeeds()` 在首次启动时把内置供应商（Kie Seedream / Volcengine Seedance / **APIMart** 等）塞进 catalog；
- 这些档案已经写好完整 `mappings`，所以 `VendorOnboardCard` 只发 `GET /models` 探活（声明 `connectionTest:'models'` 的家），不抓文档；
- 用户挑卡片 → 填 key（`upsertVendorApiKey`）即启用，无需手填请求体。

即：所谓「模型市场」实际是**代码里的 curated 供应商档案集合**，不是运行时可挑的 market JSON。路径 B 三种来源的真实落点：① 内置 seed（`seedBuiltins.ts`）；② curated vendor 源码（`catalog/*.ts`）；③ 手动录入经 `catalogCommit.commitOnboardedModelToCatalog` 落库。

### 1.4 路径 B：内置供应商（builtin seeds）—— 本地网关真正的接法

`ensureBuiltinModelSeeds`（`runtime.ts` 再导出）在首次启动时把一批内置供应商塞进 catalog（Kie Seedream / Volcengine Seedance / **APIMart** 等），由官方维护映射，用户只填 key。

**关键点**：这些内置 seed **已经有完整 mapping**，`VendorOnboardCard` 只发 `GET /models` 探活（不抓文档），所以本地网关只要协议和某个 seed 兼容，就能**直接复用**——
1. 在卡片上把「接入地址」就地改成你的网关地址（`upsertVendor({ key, baseUrlHint })`，seed 存在即跳过，用户改动不被启动刷回）；
2. 填 user_key 解锁（`upsertVendorApiKey`）；
3. 聊天/生图/视频立即可用，因为 mapping 已经是现成的。

### 1.5 本地 / 私有网关的正确落法（以本地 Lovart 网关 `apimart-gateway` 为例）

你的 `apimart-gateway`（跑在 `:9004`，后端 Lovart，OpenAI 兼容形态）协议和内置 **APIMart** seed 完全一致。但**不要复用 apimart 卡**——apimart 是付费核心变现通道，动了影响正常付费用户（用户明确要求，2026-08-10）。正确做法是**为本地网关新建一个独立 curated vendor**，复用协议兼容的 mapping 形状：

**A. 长期固化（已验证的主路径，推荐）**：写一份独立 curated 档案并注册，Nomi 重启后自动出现一张干净卡：
1. 建 `electron/catalog/lovartVendor.ts`：vendor 定义（`key:'lovart'`、`baseUrl:'http://127.0.0.1:9004'`、`authType:'bearer'`）+ 图片/视频轮询 op（`GET /v1/tasks/{task_id}`）+ 状态归一映射。**baseUrl 裸写**（不带 `/v1`，op path 自带头，见 §2.2）。
2. 建 `lovartImages.ts` / `lovartVideos.ts` / `lovartTexts.ts`：curated 模型，`modelKey` 用网关 `/v1/models` 返回的真 id（如 `gpt-image-2`、`nano-bn-pro`、`seedance-2`、`lovart-chat`），映射复用 apimart 的扁平 body 形状，参数经 `paramMap` 翻译（`aspect_ratio→size`、`resolution` 转小写、drop 网关不读的 `output_format`/`generate_audio`）。
3. 在 `seedBuiltins.ts` 注册：`seedVendor` + `reconcileModels` + `reconcileMappings`（幂等，`mapping.id` 必须用 `modelKey` 拼、不能只用 `archetypeId`，否则多个变体撞 id 导致幂等性破坏）。
4. 在 `src/config/knownVendors.ts` 加 `KNOWN_VENDORS` 卡（`connectionTest:'models'` → 探活 `GET /v1/models`），并同步 `src/i18n/locales/onboardingProviders.ts` 的中/英文案。
5. **必须重启 Nomi**：seed 只在启动加载 catalog 时跑一次（`applyBuiltinSeeds`），不重启新 vendor 不会生效（见下方踩坑 ②）。
6. 重启后：接入面板出现 Lovart 卡 → 填 key（网关 `.env` 里 `OPEN_RELAY=true` 时任意，否则填 `USER_KEYS` 里的 user_key）→ 解锁 → 探活 `GET /v1/models` 通过 → 生图/视频/聊天立即可用。

**B. 一次性临时接（不固化）**：若只是临时想连，复用协议兼容的内置 seed 卡改 baseUrl 也行——但若该卡是**付费核心通道**（如 apimart），会污染正常付费用户，不推荐。

> **协议核对表（已验证，两端逐项匹配）**：

| 能力 | Nomi mapping 期望 | 网关实际返回 | 匹配 |
|---|---|---|---|
| 探活 `GET /v1/models` | Bearer → 模型列表 | 有 | ✅ |
| 生图 `POST /v1/images/generations` | `{code,data:[{task_id}]}` | 返回**数组** `[{status,task_id}]` | ✅ |
| 视频 `POST /v1/videos/generations` | `data[0].task_id` | 返回**对象** `data:{id,status,task_id}` | ✅（`extractTaskId` 兜底取 `data.task_id`，或 mapping 直接写 `data.task_id`）|
| 轮询 `GET /v1/tasks/{id}` | `data.id/status/result.{images\|videos}` | 同构 | ✅ |
| 聊天（文本大脑） | AI SDK `POST /v1/chat/completions` | 有 | ✅ |
| 音频（配音/转写） | `/v1/audio/speech`、`/v1/audio/transcriptions` | **诚实 501**（Lovart 无 TTS/STT） | ⚠️ 已知限制，不启用声音节点走它 |

> **绝不走「添加一个 AI 模型」表单（路径 A）**：那个流程会去 `http://127.0.0.1:9004` 抓官方文档 → 失败 → 整批模型 "0/N 可用能力"（见 §1.6）。

**踩坑 ②：接本地网关最常见的"卡已建但显示未通过"根因 —— 旧脏 vendor 占位 + 没重启**

实操中「未通过」往往不是探活代码或网关问题，而是两件事叠加：
- **旧的手动中转 vendor 顶了位**：之前用旧版"添加模型"向导手动建过一个 vendor（如 `local-9004`），它 `enabled:false` 且带着**文档适配器失败残留**（`meta.adapter.state:"failed"`、`error:"Invalid URL"`、`stage:"docs"`）。这种卡 enabled=false → 模型清单 0 个、探活自然"未通过"。
- **改了代码没重启**：`applyBuiltinSeeds` 只在 Nomi 启动时跑一次，新 seed 不重启不生效。

排查手法：读 `%APPDATA%\nomi\model-catalog.json`，`grep` 该 vendor 的 `key` / `enabled` / `providerKind` / 模型 `meta.adapter.state`。**处理**：把旧脏 vendor + 它名下模型 + `apiKeysByVendor` 里对应 key 从 catalog 清掉（先备份 `model-catalog.json.bak`），然后重启 Nomi 触发新 seed。

### 1.6 报错根因：`No official API documentation could be discovered on the provider site`

**现象**：路径 A 填完表单点验证，结果 "已验证 N/N 个模型，0/N 已有可用能力"，每个模型都"未通过"，并看到这句提示。

**根因**（定位代码：`providerAdapter/service.ts::process()` 第 478-484 行）：
```ts
this.setStage(id, "discovering_docs");
const docs = await this.dependencies.discover({ baseUrl, modelKeys });
if (docs.sources.length === 0 || !docs.corpus.trim())
  throw new Error("No official API documentation could be discovered on the provider site");
```
整套适配器验证（adapterStart）**第一步就抓官方文档**（`discoverProviderDocs`，`docsDiscovery.ts`）。它对 `baseUrl` 跑一批候选 URL（`/llms.txt`、`/openapi.json`、`/docs`…），只对 `https`/`http` 的 provider 站点发请求。本地网关 `http://127.0.0.1:9004`：
- `seedUrls` 生成 `127.0.0.1`/docs.127.0.0.1 等 URL；
- `isProviderSite` 判定域名，但 fetch 全失败（localhost 无文档站 / 非公开站点）；
- `sources.length === 0` → **throw** → `finishWithError("failed")` → 所有模型的每个 mode 全部 failed。

**所以它不是"警告"，是整批失败的根因**——发生在文档发现阶段，连 `chat/completions` 都没真探。这和你填的 key 对不对、baseUrl 带不带 `/v1` **无关**（那是更深一层的验证，根本没跑到）。

**解法**：不要走路径 A。改用 §1.5 的**新建独立 curated vendor** 落法（或复用协议兼容的非付费 seed 卡）。

### 1.7 路径 A 的验证（"适配器自动编译"向导，仅云厂商用）

路径 A 的验证走 `ProviderAdapterService.process()` 分阶段：
`collecting_models`（拉模型清单）→ `discovering_docs`（抓文档，**本地网关死在这**）→ `compiling_adapter`（用文档+模板编译 mapping）→ `verifying`（逐模型调各 mode 探针）→ `finalizing`（写 catalog + 启动）。

录入后用 `testModelCatalogMapping`（`catalogCommit.ts`）→ 内部调 `execute_test_curl`（`ai/onboarding/tools.ts`），**复用和生产同样的 `buildHttpRequest`**。所以向导测通 = 生产能通，这是 P1 单一真相源的直接红利（但前提是文档发现能过）。

## 2. 统一请求构建管线（所有请求头的总出处）

代码位置：`electron/ai/requestPipeline.ts` + `electron/catalog/profileHttpRequest.ts`。

### 2.1 模板引擎 `{{...}}`

所有请求体/路径/头都是模板，变量来自 `buildTemplateContext` 给出的上下文：

| 占位符 | 含义 |
|---|---|
| `{{request.prompt}}` | 用户提示词 |
| `{{request.params.<key>}}` | 透传生成参数（width/height/seed/duration…） |
| `{{model.modelKey}}` / `{{model.model_key}}` / `{{model.model_alias}}` | 模型标识 |
| `{{user_api_key}}` | 用户 API key（onboarding 标准名） |
| `{{account.api_key}}` / `{{account.account_key}}` | 同上（legacy 手写兼容） |
| `{{providerMeta.task_id}}` / `{{providerMeta.query_id}}` | 异步任务的查询 id（轮询时用） |

模板支持整串匹配（对象/数组原样透传）与字符串插值两种模式（`renderTemplateString` / `renderTemplateValue`）。

### 2.2 URL 拼接 `joinUrl`（含版本段去重）

`vendorEndpoint.ts::endpoint` → 委托 `requestPipeline.joinUrl`。规则：
- 绝对 URL（含 `http`）直接用。
- base 去掉尾部 `/`，op path 自动补 `/`。
- **版本段去重**：若 base 以 `/vN` 结尾且 op path 又从 `/v1/` 起，则砍掉 path 的 `/v1`，避免拼成 `.../v1/v1/...`（曾导致 code-newcli-com 404）。
- `pathFrom: "host-root"` 的操作（如火山方舟 `/api/v3/...`）会先 `hostRootBase()` 剥掉 base 尾部 `/vN`，防止拼成 `.../v1/api/v3/...`。

> **和 §1.5 的关联**：这就是为什么卡片上填 baseUrl 时**不要自己带 `/v1`**——seed 的 op path 已经是 `/v1/chat/completions` 这类，joinUrl 会正确拼接；若你填 `http://127.0.0.1:9004/v1`，而 op path 又是 `/v1/...`，去重逻辑会处理，但为保险起见按卡片默认（裸 host）填最稳。路径 A 的 `probeOneProtocol` 是**另一套**拼接（裸拼 `/chat/completions`，不补 `/v1`），所以路径 A 下必须带 `/v1`——两条路径拼接规则不同，别混淆。

### 2.3 鉴权头（authHeaders）

```ts
authType === "x-api-key"  → { [headerName || "X-API-Key"]: apiKey }
authType === "bearer"     → { Authorization: `Bearer ${apiKey}` }
authType === "query"      → 无头，改走 query 参数 api_key
authType === "none"       → 无头
```

### 2.4 头合并顺序（详见 §3）

`buildHttpRequest` 里头的合并优先级（后者覆盖前者）：
```
authHeaders  ←  基础鉴权
  + extraHeaders(vendor.meta.extraHeaders)  ←  中转/网关自定义头
  + renderedHeaders(mapping 里写的 headers)  ←  映射显式头，最终裁决
```
最后按 Content-Type 兜底：非 GET/HEAD 且无显式 Content-Type 时自动加 `Content-Type: application/json`。

## 3. 所有请求头清单（一次列全）

Nomi 实际会发出的请求头，按"来源"分三类。最终请求头是这三类的合并：

### 3.1 鉴权类（由 `authType` 决定，requestPipeline.authHeaders）

| 头 | 触发条件 |
|---|---|
| `Authorization: Bearer <key>` | `authType: "bearer"`（最常见，OpenAI 兼容） |
| `X-API-Key: <key>`（或 `meta.authHeaderName` 指定的名字） | `authType: "x-api-key"` |
| （无） | `authType: "none"` 或 `authType: "query"` |

> `query` 型不走头，而是 `api_key=<key>` 拼到 URL（`authQueryParams`）。

### 3.2 中转/网关自定义头（vendor.meta.extraHeaders）

用户手动录入的任意 `key: value` 头。**用途**：很多中转网关（Relay / One-API 类）需要在 `Authorization` 之外再带一个 Header（如网关签名、渠道 id、租户标识）。这些头作为"基础层"注入，所以**图像/视频路径也能带上和聊天路径一致的网关头**（之前只有 AI SDK 路径带，这是个已修的不一致 bug）。

读取入口：`catalogStore.extractVendorExtraHeaders(vendor)` → `meta.extraHeaders` 字符串映射；聊天路径经 `buildLanguageModelForVendor` 传给 `buildAiSdkModel({ headers })`；图像/视频路径经 `buildProfileHttpRequest(extraHeaders)` 透传进 `buildHttpRequest`。

### 3.3 映射显式头（mapping.operations[].headers）

每个 HTTP 操作模板自己写的 `headers`（如 `Content-Type: multipart/form-data`、特定供应商要求的 `X-Request-Id`）。**优先级最高**，能覆盖上面所有头（包括把 `Authorization` 覆盖掉——所以模板里若写 `Authorization: Bearer {{user_api_key}}` 必须确保上下文有 `user_api_key`，否则会被空值盖掉正确鉴权；核心修正见 requestPipeline 注释）。

### 3.4 运行时自动补的头

| 头 | 生成位置 | 条件 |
|---|---|---|
| `Content-Type: application/json` | `buildHttpRequest` | 非 GET/HEAD 且映射未显式写 Content-Type |
| `Content-Type: multipart/form-data; boundary=...` | `requestMultipart`（vendorHttp.ts） | 多部件上传（图生图/参考图上传） |
| `Accept` / `User-Agent` 等 | 由底层 `fetch` / AI SDK / undici 默认带 | — |

### 3.5 日志脱敏

`redactHeaders` 会把 `authorization` / `api-key` / `token` 类的头值打成 `[redacted]`，所以请求预览/日志里看不到真实 key。

## 4. 三条生成机制的调用链

### 4.1 聊天（文本 / chat）

**路径**：`runtime.runTask(chat 分支)` → `executeTextTask`（`textTaskRunner.ts`）→ `streamTextTask`（`ai/streamTextTask.ts`）→ `buildLanguageModelForVendor`（`ai/vendorLanguageModel.ts`）→ `buildAiSdkModel`（`ai/buildAiSdkModel.ts`）→ **Vercel AI SDK `streamText`**。

要点：
- 走 **AI SDK**，不是手拼 `/v1/chat/completions`（已统一收口）。
- 鉴权/头来自 `vendor`：`providerKind` 决定 baseURL 拼法（anthropic 用原样 baseUrl，其余补 `/v1`），`apiKey` 进 AI SDK，`extraHeaders` 进 `headers`。
- 双超时闸（防中转卡死）：首字 30s、整体 120s，超时即 abort 并落节点 error 可重试。
- `image_to_prompt` 把参考图当多模态 image part 一并喂。
- 返回 `raw` 合成成 OpenAI `choices[].message.content` 形状，渲染层照旧解析。
- 流式：`runTextTaskStream` 传 `onDelta` 逐 token 回调给渲染层增量写节点。

### 4.2 生图（image）

**路径**：`runtime.runTask(image 分支)` → `findExecutableModel` 拿到 (vendor, model, mapping) → `buildProfileHttpRequest`（用 mapping 的 `text_to_image` / `image_edit` 操作模板）→ `vendorHttp.requestJson` 或 `requestMultipart` → 解析响应资产 URL → 本地化落盘（`assetLocalization` + `projectAssetStore`）。

要点：
- **不**走 AI SDK，走自建 `requestPipeline` + `vendorHttp`（因为图像 API 各家形状差异大，用 mapping 模板表达）。
- kind 判定：`image` intent 带参考图 → `image_edit`（图生图）；否则 `text_to_image`（`capabilityCore/core.ts::defaultKindForIntent`）。
- 异步厂商（如 modelscope）首调返 `queued` → `taskCache` + `fetchTaskResultFn` 轮询到终态。
- 参考图来源优先级：`input.references` → 节点 `references` → 画布参考**入边**解析（`referencesFromEdges`，headless 路兜底，修复"连了参考边但被无视"的 bug）。
- 多部件：图生图/上传走 `requestMultipart`。

### 4.3 视频（video）

同生图路径，但 kind 为 `text_to_video` / `image_to_video`，且：
- 轮询超时更长（300s vs 图 240s），轮询间隔 3s（图 1.5s，符合厂商查询间隔要求）。
- 同样支持异步厂商轮询。
- 资产本地化时会探测时长（`probeLocalizedDurationSeconds`）。

### 4.4 编排层（headless / CLI / MCP 入口）

`electron/capabilityCore/core.ts::generateOnProject` 是"外部 agent 驱动 Nomi"的主进程单一执行口：
1. 解析/新建画布节点，把节点置 `queued`。
2. 付费确认（`gateway.confirmSpend` → 主进程 `assertAndConsumeSpendGrant` 硬闸，未确认 fail-fast，不烧额度）。
3. 置 `running`，构造高层 `TaskRequest`（`kind` / `prompt` / `extras`），注入 `grantId` + `idempotencyKey`。
4. 调注入式 `runTaskFn`（生产即 `runtime.runTask`）。
5. 异步厂商本进程内轮询到终态（taskCache 进程级，不能跨调用轮询）。
6. 结果写回节点（图/视频/音频走首资产，文本走 `result.raw`）。

### 4.5 参考素材（图片）传递机制 — Lovart 全链路重新核实（2026-08-10 复查修正）

> 本节是对上午 §4.5 的**重新核实 + 修正**：上午的结论（"CURATED 没 lovart""聊天没本地化"）经下午实读代码与网关日志核对，**两处已被修复**，但**聊天助手(不是画布节点)那一路仍是真正漏图口子**。下面按"三条真实链路 + 网关实证"重写，避免误导。

#### 4.5.1 三条图片链路的真实形态（逐个读代码核对）

本地图片一律 `nomi-local://`（见 `referenceUrl.ts::asUrl` 白名单）。发送前必须换成"供应商可达形态"，否则下游解析不了。三条路形态不同：

| 链路 | 代码路径 | 图片最终形态 | 是否本地化 |
|---|---|---|---|
| **① 画布「图生图 / 视频」节点** | `runtime.buildHttpRequest` → `localizeAssetsForVendor` → 进 create op `image_urls` | `nomi-local://` 被转成 **`data:` base64**（Lovart 走 `inline-base64` 策略） | ✅ 已本地化 |
| **② 画布「聊天/以图生提示」`image_to_prompt`** | `textTaskRunner.executeTextTask` → `localizeAssetsForVendor` → `firstReferenceImage` → `streamTextTask.toImagePart` | 同①转 `data:` base64 → `/v1/chat/completions` 的 `image_url.url` | ✅ 已本地化（textTaskRunner.ts:35-52 已修） |
| **③ 助手聊天 Agent Chat V2（用户截图用的「Lovart Chat」入口）** | `agentChatV2.runAgentChatV2` → `buildAgentUserContent` → `readNomiLocalAsset(url)` 直接读字节 → AI SDK `image` part | `nomi-local://` **不本地化**，直接读字节塞进 AI SDK，由 SDK 序列化成 `data: base64` | ❌ **不本地化，但也不依赖本地化** |

**关键认知（纠上午的错）**：第③路**不调** `localizeAssetsForVendor`，但它**也不需要**——它走标准 OpenAI `/v1/chat/completions`（`buildAiSdkModel` → `createOpenAICompatible`），AI SDK 对 `{type:'image', image: Uint8Array}` 会自动序列化成 `data:image/...;base64,...`，而 Lovart 网关 `resolve_attachments` **认 `data:` 格式**（见 4.5.3）。所以第③路图片能否到达，取决于**字节是否真读到了**，不是格式转换问题。

#### 4.5.2 第③路（助手聊天）真正漏图的根因（= 用户"一直提示没图片"的真因）

> **Lovart 本身支持图片聊天**（用户已确认：聊天模型 `lovart-chat` 走标准 OpenAI `/v1/chat/completions`，网关 main.py:960 收 OpenAI 兼容消息，含 `image_url`）。所以根因**不在 Lovart**。问题 100% 在 **Nomi 端**——发出去的请求里压根没有图，或图字段为空。逐帧钉死：

**发送链路（实测代码）**：
1. 前端 composer 把附件上传成本地图 → `nomi-local://asset/<projectId>/...`（useComposerAttachments.ts:62，"已上传为 nomi-local"）。
2. 渲染层只把 `url` 透传给 IPC（`AgentAttachmentPayload` 只带 url/contentType/fileName，**不带字节**，desktopAgentsChatStream.ts:9-16）。
3. 主进程 `agentChatV2.ts:523-533` 用 `readNomiLocalAsset(url)` 把 `nomi-local://` 读成字节，塞进 AI SDK 的 `image` part。
4. AI SDK（openai-compatible）→ 自动把字节序列化成 `data:image/...;base64` 内联进 `image_url.url` → 发 `POST /v1/chat/completions`。

**两个真凶（任一命中即静默丢图，模型只收到纯文字 → 说"没看到图片"）**：

**真凶 A（已实证，就是它）—— `lovart-chat` 被判为"不支持图片" → 整张静默丢**
- `agentChatV2.ts:526`：`supportsImageInput: modelSupportsImageInput(model.modelKey, model.modelAlias, model.meta)`。
- `lovartTexts.ts:14` 定义 `{ modelKey:"lovart-chat", labelZh:"Lovart Chat" }` —— **没有 `meta`**。
- `modelSupportsImageInput`（agentUserContent.ts:33-37）：meta 没声明 → 走 `VISION_MODEL_RE`（line 19：`gpt-4o|claude|gemini|...`）。`lovart-chat` 不匹配任何 vision 关键词 → **返回 `false`**。
- → `agentUserContent.ts:69` `if (!supportsImageInput) { droppedImages += 1; continue }` → **图片被整张静默丢弃，连"不支持图片输入"提示都没有**（line 72 那条注记只在 `resolveBytes===null` 时触发，这里更早 return）。
- **结论**：Lovart 侧完全正常、支持图片聊天；是 **Nomi 自己判定 Lovart 不支持图，把图丢了**。这就是"一直提示没有图片"的 100% 根因。图生图/视频（走 `localizeAssetsForVendor`）不受影响，因那是另一条带图路径。

**修复落点（一行，守 P1 不并行）**：`lovartTexts.ts` 给 `lovart-chat` 补 `meta: { supportsImageInput: true }`，让 `modelSupportsImageInput` 命中显式声明返回 true。这是唯一真因修复，无需改 agentChatV2/agentUserContent。

**真凶 B — `readNomiLocalAsset` 返回 null → 丢**
`agentChatV2.ts:528-531` → `localAssetFile.ts:60-100`。`readNomiLocalAsset` 必须同时满足才返回字节，否则 `null`：
- URL 前缀是 `nomi-local://asset/`（`file://`/相对路径/裸 base64 → null）；
- 文件真实存在且是文件（`fs.existsSync && isFile`，被删/落盘失败/`.meta` 旧路径失效 → null）。
返回 null → `agentUserContent.ts:70-71` `droppedImages++` 静默丢。

> 验证方式（不用猜）：开 `LAB_DEBUG_REQUESTS=1`，聊天带图发一次，看 `/tmp/lab-request-*.json` 的 `messages[].content` 里有没有 `image_url`、其 `url` 是不是 `data:image/...;base64,...` 且非空。**有 image_url 但 Lovart 说没图**= Lovart 侧问题；**根本没有 image_url**= Nomi 侧（真凶 A 或 B）。

> 图生图/视频（①）**不会**有这问题：`localizeAssetsForVendor` 已把 `nomi-local://` 转 `data:` base64 塞进 create op 的 `image_urls`，网关认 `data:`（见 4.5.3）。所以"图生图/视频也肯定有这问题"在机制上不成立——那两条路已修且网关兼容。聊天漏图是**第③路独立的问题**（走 AI SDK 直发，不经过 `localizeAssetsForVendor`）。

#### 4.5.3 网关侧实证（日志对照，证明网关无锅）

读 `apimart-gateway/logs/apimart_9004.log`（2026-08-10 当天）：

```
10:27:13  POST /lovart/chat-with 200 ← 这是网关【内部】转发给 Lovart 上游的路径（main.py 里 /v1/chat/completions 的处理函数转调 client.chat）
10:27:13  resolve_attachments: 命中 attachments 1 个 → upload_file 200 → URL=https://cdn.lovart.ai/...  ← 走「attachments 字段」中转时才触发
10:27:14  POST /lovart/images/generations 200 ← 图生图成功
10:27:14  upload_file 200 → 参考图已落地 Lovart CDN
```

**结论**：网关对 `http(s)` 回环自下载 / `data:` base64 / 裸 base64 均正常接收（main.py::resolve_attachments 认这三类，只跳 `nomi-local://` 与 `file://`）。**"没有图片"不是网关侧丢弃。**

**关键纠正（2026-08-10 下午重读 main.py:1002 实证的链路，推翻上一版结论）**：之前以为聊天走"内联路径、不经过 `resolve_attachments`"——**错了**。实测 `chat_completions`（main.py:960）在收到 `vision_urls = [data: base64...]` 后，第 **1002 行**显式调 `TaskService.resolve_attachments(client, vision_urls)`，把 `data:` base64 **先 upload 到 Lovart CDN、换成 CDN URL 再 `send_with_project(attachments=...)` 发上游**。即：

```
聊天带图：Nomi 发 data: 内联 → 网关 chat_completions(main.py:1002) → resolve_attachments → upload_file → Lovart CDN → 上游 chat(attachments=CDN URL)
图生图/视频：Nomi 发 data: 内联 → 网关 resolve_attachments → upload_file → Lovart CDN → 上游 generations(attachments=CDN URL)
```

**两条路在网关侧共用同一个 `upload_file` 环节**，都依赖 Lovart 上游 `/file/upload` 可达。所以：
- "聊天图片/图生图上传失败"是**同一个故障点**（上游 `/file/upload` 直连+代理均不可达），不是两条独立问题。
- 我下午那处 `supportsImageInput: true` 修复的验证意义在于：修复前 Nomi 在本地就静默丢图（Lovart 根本收不到 `image_url`）；修复后图确实发到网关了，才暴露出网关→上游 upload 这一跳的网络/上游问题。即"报错变了"= 修复生效，锅转移到链路末端。

## 5. 响应解析与异步轮询

- **task id 提取** `extractTaskId`：先按显式 dot-path（`response_mapping.task_id`），再探 `id/taskId/task_id/jobId`，再探 `data` 信封（`{code,msg,data:{...}}` 包裹，常见 kie 风格）。
- **逻辑错误探测** `looksLikeLogicalError`：很多厂商 HTTP 200 但包业务错误码（kie `{code:4xx}`、RunningHub `{errorCode:"1014"}`），不探测会被误判成功。
- **状态解析 / 资产 URL 提取 / 响应变换**：`tasks/responseParsing.ts` + `responseTransforms.ts` + `assetUrlExtract.ts`，由 mapping 的 `response_mapping` 配置驱动。
- **轮询**：`taskCache`（TtlLruCache）+ `fetchTaskResultFn`，终态集合 `{succeeded, failed}`。

## 6. 给开发者的"加一个新供应商"最小清单

1. **只想接 OpenAI 兼容聊天（公有云）**：用户在 UI 录入 baseUrl + key + providerKind=`openai-compatible` 即可，零代码。但注意路径 A 仍需官方文档（§1.6）。
2. **接有自己请求/响应形状的生图/视频厂商（公有云）**：
   - 在 `electron/catalog/` 写一份 curated TypeScript 档案（如 `catalog/<vendor>Vendor.ts` + `<vendor>Images.ts` 等），定义 `vendor` + `models` + `mappings`，mapping 写清 `operations[].method/path/headers/body` 与 `response_mapping`（task_id / status / asset url 的 dot-path）；并在 `seedBuiltins.ts` 注册该 vendor。
   - `authType` 选 `bearer` / `x-api-key` / `query` / `none`。
   - 需要网关额外头 → 用户填 `meta.extraHeaders`（不用改代码）。
   - 用"适配器自动编译"向导验证（**仅当厂商有公开文档站**）。
3. **接本地 / 私有中转网关**（如自建 Lovart 网关）：**不要走路径 A**。正确做法（已验证）：
   - **写一份独立 curated vendor 档案**（`lovartVendor.ts` + `lovartImages/Videos/Texts.ts`，复用协议兼容的内置 mapping 形状），注册进 `seedBuiltins` + 加 `KNOWN_VENDORS` 卡（§1.5 方案 A）；**不要复用付费核心通道的卡**（如 apimart）；
   - `mapping.id` 必须用 `modelKey` 拼（`seed-lovart-<modelKey>-<taskKind>`），不能只用 `archetypeId`——多个变体共用 archetype 会撞 id，`reconcileMappings` 幂等性被破坏（第二次 apply 反复漂移）；
   - 改完代码**必须重启 Nomi** 让 `applyBuiltinSeeds` 播一次；若已有旧手动中转占位（enabled:false + adapter failed 残留），先清 catalog（§1.5 踩坑 ②）再重启。
4. **不要**为不同供应商写两套 UI（违反 P1/P4）——能力差异全部用 mapping 数据表达。
5. 加新实现的同时删旧实现（P1 加新必删旧）。
