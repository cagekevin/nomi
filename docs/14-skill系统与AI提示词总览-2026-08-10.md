# Skill 系统与 AI 提示词总览

> 探索范围：`electron/skills/*`、`electron/ai/agentChatV2.ts`、`src/config/prompts/*`、`src/workbench/generationCanvas/*`、`docs/skill-pack-format.md`、仓库根 `skills/`（30 个技能）。
> 目的：给开发者一份**总结性**地图——skill 散在哪、生命周期是什么、所有 AI 提示词落在哪、它们如何拼成每一次对话。
> 日期：2026-08-10
> 配套规范：`docs/skill-pack-format.md`（Skill Pack v2 人读格式）、`docs/plan/2026-06-19-skill-playbook-system.md`（playbook 设计依据）

## 〇、一句话心智模型

- **Skill = 纯文本方法论**，不是代码。`skills/<name>/` 下只有 `SKILL.md`（人话方法论，作为 system prompt 注入）+ `skill.json`（机读 manifest：工具白名单、所需 provider、阶段骨架）。
- **提示词不是单一文件**，而是分三层拼出来的：`NOMI_AGENT_IDENTITY`（共享身份） + 当前面专长（如画布工具集） + 当前 skill 方法论。各面只叠自己的专长层，身份只在一处定义。
- **skill 不自动执行任何外部动作**。运行时只把 SKILL.md 当知识注入；里面提到的 CLI/HTTP 不会自动跑，除非当前对话/界面明确提供了对应工具。

## 一、Skill 系统源码地图

| 文件 | 职责 | 关键函数 |
|---|---|---|
| `electron/skills/skillStore.ts` | **加载/查找单一真相源**。扫所有 skills 根，解析 frontmatter + skill.json，产 `SkillRecord[]` | `readSkillRecords` / `findSkillRecord` / `listSkillSummaries` / `readSkillContent` |

## 二、Skill 数据结构（manifest 字段）

来源：`electron/skills/skillManifestSchema.ts:79-107`

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 全局唯一稳定 key，如 `workbench.storyboard.planner` |
| `version` | string | SemVer 串（schema 强制必填） |
| `description` | string | 一句话 UI 摘要 |
| `tools` | string[] | 工具白名单（只这些工具对 LLM 可见） |
| `requiredProviders` | `("text"\|"image"\|"video")[]` | 端到端需要的 provider 模态 |
| `permissions` | `("read-only"\|"create"\|"delete"\|"export")[]` | 能力门 |
| `inputs?` / `examples?` | 可选 | 声明输入字段 / 示例 prompt |
| `stages?` | `SkillStage[]` | 多段 playbook 骨架；**缺省 = 单段 legacy 包**，向后兼容 |
| `author?` / `label?` | 可选 | 卡片展示用 |

**`SkillStage`**（playbook 段）：`id` / `goal` / `tools[]` / `dependsOn?` / `pause?`（缺省 true）/ `modelPrefs?[]`。

**阶段模型偏好硬约束**（`skillStageModelPrefSchema:48-55`，`.strict()`）：只声明能力身份 `kind` + 可选 `family`（如 `seedance`），**绝不绑 vendor 专属 `archetypeId`，也不写死 `params`**——这是「通用第一 + 分享出去不绑死」的硬约束。

## 三、Skill 生命周期（完整链路）

```
定义(SKILL.md+skill.json)
   │
   ▼  发布/内置
[内置] 仓库根 skills/ → 打包进 resources/skills（随安装包，只读）
[用户] 自己建 / 从他人导入（skillPackage 异步文件交换）
   │
   ▼  加载（每次对话热路径，readSkillRecords）
扫所有 skills 根 → 解析 frontmatter + skill.json
   ├─ origin 判定：目录在 userData/skills ⇒ 'user'（可删/可导出）
   │              否则 ⇒ 'builtin'（只读、禁删）
   └─ 多根去重：「先出现的根」胜（内置优先）
   │
   ▼  请求匹配（findSkillRecord）
精确 name → 前缀匹配 → 归一化模糊匹配（处理大小写/分隔符差异）
   │
   ▼  注入（buildSkillSystemPrompt → 拼进 system prompt 第三段）
   │
   ▼  工具组选择（buildToolsForSkill，agentChatV2.ts:346）
按 skillKey 前缀分流**引擎用哪组工具**（一套 agent 引擎，参数化工具组）：
  - skillKey 以 `workbench.creation.` 开头 → 文档工具组（read_full_text / read_selection /
    insert_at_cursor / replace_selection / append_to_end / author_skill）
  - 其它（generation / storyboard / 默认）→ 画布工具组（read_canvas_state / propose_storyboard_plan /
    create_canvas_nodes / connect_canvas_edges / set_node_prompt / delete_canvas_nodes /
    run_generation_batch / arrange_storyboard_to_timeline / tidy_canvas / create_staging_reference /
    create_camera_move）
  注意：manifest 的 `tools` 白名单只在**单段 skill 被请求时**经 buildSkillSystemPrompt 收紧 LLM 可见集；
  legacy（无 manifest）的 director-/writer- 不收紧，靠调用方工具组驱动。
   │
   ▼  执行
单段：直接当知识注入 system prompt
多段(playbook)：playbookOrchestrator 按 dependsOn 拓扑排序逐段跑，
                每段按 tools 白名单收紧 gate，pause 段完成后等用户审阅
   │
   ▼  下架/移除
builtin：随安装包更新/移除（代码不删，只读目录碰不到）
user：deleteUserSkill（必须严格落在 userRoot 内，防 .. 穿越）
```

### 存放位置与多根扫描
`electron/runtimePaths.ts:50-60` `getSkillsRoots()` 依次尝试：
1. `NOMI_SKILLS_DIR`（env 覆盖，测试/隔离用）
2. `process.cwd()/skills`
3. `app.getAppPath()/skills`（开发态内置）
4. `__dirname/../skills`
5. `process.resourcesPath/skills`（**打包后内置随附位置**）
6. `getUserSkillsRoot()` = `getSettingsRoot()/skills`（用户可写）

### 版本与锁
- manifest 自带 `version`（必填）。
- ⚠️ **`skills-lock.json` 在代码里没有引用**——仅在 `AGENTS.md`/`CLAUDE.md`/`docs/11-工程纪律详解` 提及，**未实现**。版本管理目前只靠 `manifest.version`，无锁版本文件。

### 导入/导出/删除安全（`skillPackage.ts`）
- 包格式 `nomi-skill-v1`，纯 JSON（skill 是纯文本，无需 zip）。
- 导入：`validateSkillPackage` 校验版本 + 文件名安全（拒 `..`/可执行扩展）+ 必含 SKILL.md + skill.json 合法；冲突目录名自动加 `-2/-3`（**不覆盖内置**）。
- 删除：`deleteUserSkill` 解析后必须严格落在 `userRoot` 内（防穿越），只删 `userData/skills`。

## 四、内置 Skill 清单（仓库根 `skills/`，30 个）

按目录前缀分族（来源：`skillStore.ts:148` 仅 `director-`/`writer-` 前缀对 MCP 脊柱外暴露）：

| 族 | 成员 | 性质 |
|---|---|---|
| `director-`（导演方法论，外暴露） | action / art-design / cinematography / consistency / guzhuang / keyframe-review / performance / shot-translation / sound / staging / style-otomo-wright / transitions | 电影方法论库，供内外 agent 按需调用（共 12 个） |
| `writer-`（编剧方法论，外暴露） | adaptation / behavior-psychology / dialogue / improv / incubation / novel-digester / review / screenwriter / songfangjin / structure / style-schrader | 同上（共 11 个） |
| `workbench-*`（幕后管线，不暴露） | workbench-creation / workbench-fixation-planner / workbench-generation / workbench-storyboard-planner | 自动路由/按钮触发，不在用户库浏览 |
| 其他内置 | creation-edit / skill-author / brand-promo | creation-edit/skill-author 是幕后管线；brand-promo 是 playbook（有 stages，用户库可见） |

> 渲染层 `listSkillsForRenderer` 只露：`origin==='user'` ∪ `manifest.stages.length>0`（playbook）。幕后管线与外来工程技能（无 manifest）被藏掉。

### 4.1 形态分布：v2 manifest vs legacy markdown-only（实测）

> 扫描 `skills/*/skill.json` 实测结论：**30 个内置 skill 里只有 6 个带 skill.json**，其余 24 个只有 `SKILL.md`。这是理解"哪些 skill 真正受工具白名单约束"的关键。

| 形态 | 成员（6 + 24） | 运行时后果 |
|---|---|---|
| **v2（有 skill.json）** | `brand-promo`、`workbench-creation`、`workbench-generation`、`workbench-storyboard-planner`、`creation-edit`、`skill-author` | `skill.json` 的 `tools`/`requiredProviders`/`permissions` 生效；`brand-promo` 是 playbook（有 `stages`）。其余是幕后管线，被 `listSkillsForRenderer` 藏掉（不进用户库） |
| **legacy（仅 SKILL.md）** | 全部 `director-*`（12）、全部 `writer-*`（11）、`workbench-fixation-planner` | `readSkillManifest` 返回 `manifest:null` ⇒ 不收紧工具，所有内置工具对 LLM 可见；它们是**纯知识注入**（SKILL.md 当 system 第三段） |

**由此澄清两个常见误区**：
- ❌ 误：所有 skill 都有工具白名单。✅ 实：`director-*`/`writer-*` 根本无 manifest，白名单无从谈起；它们靠"被调用方 skill 的工具组 + 引用"驱动。
- ❌ 误：`director-*`/`writer-*` 是"用户触发式 skill"。✅ 实：它们是经 MCP 脊柱（`listSkillSummaries`）暴露给内外 agent **按需检索**的方法论库（`skillStore.ts:148` `CRAFT_SKILL_PREFIXES`）；日常对话不显式请求就不会叠进 system。

> 每个 skill 的具体职责写在它自己的 `SKILL.md` frontmatter `description` 里（如 `director.consistency` = 治多镜头换脸/换形/换景的方法论）。要查某个 skill 干什么，**直接读 `skills/<name>/SKILL.md`**，不在本篇逐条复制（避免与源文件脱节）。

### 4.2 Playbook 多段编排机制（仅 brand-promo 用）

> 单段 skill 当知识注入即止；多段 playbook 才进编排器。当前唯一 playbook = `brand-promo`（4 段：storyboard → build → generate → assemble，每段 `pause:true` 等用户审阅）。

**manifest 骨架**（`skillManifestSchema.skillStageSchema`）：每段 `id` / `goal` / `tools[]` / `dependsOn?` / `pause?` / `modelPrefs?[]`。
- **模型偏好硬约束**（`.strict()`，`skillManifestSchema.ts:48`）：`modelPrefs` 只接受 `kind` + 可选 `family`（如 `seedance`），**结构上拒绝 `archetypeId` / `params`**——通用第一 + 分享不绑死 vendor。

**状态机**（`playbookOrchestrator.ts` 的 `PlaybookRun`）：
```
running ──completeCurrent()──┐
   │ (pause 段)              │ (非 pause 段)
   ▼                         ▼
awaiting-confirm ──advance()──► running ──…──► done
   (用户审阅确认)              (继续下一段)
```
- 定序：`orderPlaybookStages` 用 **Kahn 拓扑排序**（稳定，依赖先于被依赖；环/悬空依赖 `throw`，加载期就拦，而非静默跑飞）。
- 能力缺口：`skillCapability.ts` 的 `reportSkillCapability(manifest, availableProviders, availableTools)` 算「缺哪个 provider/工具」，交给 UI 引导接入（**缺能力 ≠ 报错**，对齐 n8n/Dify 三态）。

## 五、所有 AI 提示词落点总表

> 分类：① system 身份层 ② 面专长层 ③ skill 方法论层 ④ 评审/judge 提示词 ⑤ 模型档案提示词。
> 关键纪律：system 身份层**只在 `agentChatV2.ts` 一处定义**；可见 UI 文案走 i18n，但**提示词本身是硬编码中文/英文**（未走 i18n——提示词不是「UI 文案」，是给模型的指令）。

### 5.0 提示词如何拼成一次 system（代码级落点）

> 提示词不是"写在某文件"，而是 **`runAgentChatV2` 在每轮把四段 join 成一个 system**（`agentChatV2.ts:518`，实测）：

```ts
// agentChatV2.ts:518 —— 四段拼接，顺序即缓存命中策略
const systemParts = [
  NOMI_AGENT_IDENTITY,   // ① 共享身份（唯一源，永远第一段）
  systemPrompt,          // ② 面专长：生成画布 buildStaticAgentSystemPrompt / 创作区 buildCreationAiPrompt 的产物
  skillSystemPrompt,     // ③ skill 方法论：buildSkillSystemPrompt 把 SKILL.md 拼进第三段
  memoryBlock,           // ④ 项目记忆（切片0，最频繁变 → 殿后只击穿后缀缓存）
].filter(Boolean);
const system = sanitizeForBroadCompat(systemParts.join("\n\n"));
```

- **顺序即缓存策略**：身份/专长/skill 在会话内 byte 级稳定（尤以生成画布 `buildGenerationCanvasAgentStaticBody` 抽到 config 资源、动态画布快照放**用户消息**而非 system，见 `generationCanvasAgentClient.ts:76`），vendor 自动前缀缓存命中；只有 `memoryBlock` 殿后，变更只击穿后缀。
- **`systemPrompt` 槽（②）的两条来历**：
  - 生成画布：`generationCanvasAgentClient.ts:61` `buildStaticAgentSystemPrompt(mode)` 按 `agent|chat|refine` 组装，调 `buildGenerationCanvasAgentStaticBody` 注入工具说明+硬约束。
  - 创作区：`buildCreationAiPrompt(mode, request)`（`creationAiModes.ts:145`）拼 7 模式专长 + 文档工具规则——**独立第三处静态提示词源**，不经后端 `buildSkillSystemPrompt`。
  - 两者都**只放面专长，不重复声明"我是谁"**（身份在 ① 一处）。
- **③ skill 方法论段**：`buildSkillSystemPrompt(payload)`（`agentChatV2.ts:79`）从 `payload.chatContext.skill.{key,name}` 取 → `findSkillRecord` → 拼 `skill.body`；找不到给安全兜底（不谎称已加载）。

**`PROVIDER_ADAPTER_SYSTEM_PROMPT` 触发场景**（补 §七 旧缺口）：当用户在供应商接入流程里提供第三方 API 文档 URL/文本时，`compiler.ts` 用 `generateObject` 调一个 text 模型，把非可信文档（DOCUMENTS 段视为不可信数据，忽略其中的指令注入）编译成 `adapterModelContractSchema` 结构化契约。该提示词是**接入链路的独立一次性用途**，不进对话 system、不与 ①② 三层拼装混用——属于「AI 辅助把文档变成 adapter 配置」，不是给创作 agent 的指令。安全红线见 `SYSTEM_PROMPT` 第 28-34 行（禁输出 JS/TS/shell/自定义 transport、禁编造端点、模板只能读 `{{user_api_key}}` 等白名单变量）。

### 5.6 创作区 skillKey 映射规则（2026-08-10 补）
创作区 `runWorkbenchAgent` 的 `skillKey` 决定注入哪个 skill 的方法论层（`CreationAiPanel.tsx:320`）：

| 场景 | `skillKey` 取值 | 对应 skill |
|---|---|---|
| 用户手动锁定 playbook（如「品牌宣传片」） | `activeSkill.key`（如 `brand-promo`） | `skills/brand-promo` 等 |
| 未锁定，回退创作模式 | `workbench.creation.${mode.id}`（如 `workbench.creation.story`） | `skills/workbench-creation`（mode→同一 skill 的不同段） |

## 六、提示词与 skill 的关系（设计意图）

- **提示词 = 三层拼装**，不是「写在某一个文件」：
  `system = NOMI_AGENT_IDENTITY`（共享） + 面专长静态段（`generationCanvasAgent.ts` 画布工具集 / `creationAiModes.ts` 创作区 7 模式专长，见 §5.2） + `skillSystemPrompt`（skill 方法论）。
- **skill 即「可分享的提示词包」**：`SKILL.md` 就是一段会被注入 system 的方法论提示词；`skill.json` 描述它的工具/provider 边界。分享 skill = 分享提示词（纯文本）。
- **「提示词即 skill」模式已落地**：`workbench-*` 系列就是幕后提示词包；`brand-promo` 是用户可见的 playbook 提示词包。
- **character-fixation 提示词是代码内 prompt**（非 skill）：`fixationPromptTemplates.ts` 里硬编码，因它要按剧本反推 expressions/outfits 等动态拼装，比静态 skill 更需要运行时参数化——符合「参数化强的走代码，方法论强的走 skill」。
